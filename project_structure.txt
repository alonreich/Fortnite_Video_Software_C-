3. *** ⚠️ PORTRAIT CANVAS TRAP ⚠️ ***
   The portrait (9:16) conversion does NOT use a simple center crop!
   It uses the "Portrait Canvas Trick": scale -> crop -> overlay -> compose -> pad.
   - For 1920x1080 input: scale factor = 1920/1080 = 1.778 -> 3413x1920.
   - Then it center-crops to exactly 1280px wide (Internal Space).
   - Surviving original horizontal width = 1280 / 1.778 = 720px (NOT 608px).
   THE SINGLE SOURCE OF TRUTH for all portrait math is:
   `src/FortniteVideoSoftware.Core/Media/CoordinateMath.cs`

1. THE 7 BIBLICAL NORTHSTAR ARCHITECTURE KEYPOINTS
------------------------------------------------------------------------------
Our goal is maximum GPU utilization and Zero-Copy UI integration on a C# .NET 9 NativeAOT footprint.
1. Zero-Copy Memory: Maintained. WGL_NV_DX_interop2 aliases the texture natively in the driver. Pixels never traverse the PCIe bus to the CPU.
2. Native UI Composition: Maintained. The extracted IDXGIResource.SharedHandle feeds directly into Avalonia's CompositionDrawingSurface (UpdateWithKeyedMutexAsync), preserving exact Z-index overlay rendering. No NativeControlHost/HWND hacks!
3. Maximum GPU Utilization: ⚠️ COMPROMISED BY DESIGN ⚠️.
   CRITICAL AI WARNING: DO NOT TRY TO "FIX" THIS TO `d3d11va`.
   Because libmpv strictly requires an OpenGL render API, and Avalonia strictly requires a D3D11 surface, we use `WGL_NV_DX_interop2`. Native `d3d11va` hardware decoders CANNOT initialize inside an OpenGL context without falling back to CPU software decoding.
   The mandatory fix is `hwdec=cuda,dxva2,auto-safe`. The GPU uses a microscopic "translation tax" (CUDA/DXVA2 -> OpenGL -> D3D11) completely in VRAM. It is the ONLY way to retain hardware acceleration. DO NOT OUTSMART THIS.
4. The Hybrid Graphics Compromise: Resolved. WGL-to-DX interop successfully bridges the libmpv OpenGL limitation while keeping the D3D11 surface intact for Avalonia.
5. NativeAOT Compilation: Maintained. Uses native Windows opengl32.dll and D3D11 libraries via [LibraryImport] and [UnmanagedCallersOnly]. No ANGLE/GStreamer bloat.
6. Front-End Editing: Maintained. The UI retains libmpv, preserving advanced caching and frame-accurate scrubbing for the timeline.
7. Back-End Exporting: Maintained. The FFmpeg headless encoding pipeline remains completely isolated from the UI render loop.

2. THE THREE (3) SUB-APPLICATIONS
------------------------------------------------------------------------------
The software suite comprises 3 completely separate processes to ensure strict memory isolation:
1. MAIN App: The primary application (`MainWindow.axaml`). Handles timeline, trimming, music wizard, and final export.
2. Video Merger: Joins separate videos via FFmpeg (`VideoMergerWindow.axaml`). Opened as a separate process.
3. Crop Tools: Precision canvas interface (`CropToolWindow.axaml`) to export the JSON config file that powers Portrait mode coordinates. Opened as a separate process.
AI NOTE: Do not convert Merger or Crop Tools to modal dialogs. They intentionally run as separate executables and instantly close the Main App.

5. HARDWARE RENDERING PIPELINE (THE ZERO-COPY VRAM PATH)
------------------------------------------------------------------------------
To fully understand the architecture (and the Keypoint 3 translation tax), this is the exact journey of a single video frame. The frame NEVER touches the CPU (RAM) after being read from disk; it stays entirely in GPU VRAM.

.mp4 Video File (Disk)
  ===> libmpv Demuxer (CPU/RAM parsing only)
  ===> NVIDIA/AMD Hardware Decoder (VRAM via hwdec=cuda/dxva2)  [The Translation Tax Origin]
  ===> OpenGL Framebuffer Object [FBO] (VRAM via mpv_render_context)
  ===> WGL_NV_DX_interop2 Bridge (VRAM cross-API translation)
  ===> D3D11 Shared Texture (VRAM)
  ===> IDXGIKeyedMutex (VRAM sync lock, producer/consumer handshake)
  ===> Avalonia CompositionDrawingSurface (VRAM)
  ===> The End User's Display Monitor (GPU Swapchain)

6. CURRENT CORE LOGIC & FEATURES
------------------------------------------------------------------------------
- Video Playback (MpvVideoView.cs & MpvIpcClient.cs): Uses libmpv via named pipes/IPC for robust frame-accurate seeking.
- Timeline & Markers (MainWindow.axaml.cs): Custom UI Canvas drawing for playhead (PlayheadBadge), camera cuts (ThumbnailOverlayCanvas), and freeze-frames. Implements frame-by-frame 16.66ms finesse via arrow keys for pinpoint accuracy.
- Music Wizard (MusicWizardWindow.axaml.cs): Audio waveform rendering, track synchronization, visual phase 3 preview, and persistent volume settings that remember user adjustments between sessions.
- Granular Speed Editor (GranularSpeedEditorWindow.axaml.cs): Segmented timeline speed mapping. Features an exclusive "Freeze Image" UI flow with a cascading UI light wave that completely locks down all other controls and directs users to pick a preset duration.
- Smart Text Overlays (TextOverlayGenerator.cs): SkiaSharp-based PNG generator for Mobile portrait videos. Dynamically calculates line wrapping, iteratively shrinks font sizes to fit within a strict 150px height, and includes an intelligent Bidirectional (BIDI) text tokenizer to correctly reverse Hebrew/RTL string blocks for LTR Skia rendering.
- FFmpeg Rendering (FfmpegWorker.cs, ProcessWorker.cs): Translates all UI selections (crops, time segments, speeds, audio) into complex FFmpeg filter graphs (FilterBuilder.cs) and executes them.

7. ACTIVE ARCHITECTURAL DECISIONS
------------------------------------------------------------------------------
- Decision: Pure Code-Behind UI State (vs MVVM). Rationale: Allows for rapid prototyping and absolute control over granular canvas rendering coordinates, marker bounding boxes, and dispatcher timer ticks. Tradeoffs: Results in very large .cs files (e.g., MainWindow.axaml.cs), tighter coupling between UI and logic.
- Decision: FFmpeg + SkiaSharp for Overlays. Rationale: FFmpeg's built-in drawtext filter is highly limited for dynamic line-wrapping and BIDI/RTL text rendering. Generating a transparent PNG overlay via SkiaSharp in C# and feeding it to FFmpeg is vastly more robust. Tradeoffs: Minor disk I/O cost to save/load temporary PNGs to disk before muxing.

- SkiaSharp Overlay Scaling: TextOverlayGenerator generates at exactly 1080px width; if the output resolution dynamically changes in the future, these dimensions must be proportionally scaled.

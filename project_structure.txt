FORTNITE VIDEO SOFTWARE (.NET 9 NativeAOT + Avalonia UI)
# PROJECT STRUCTURE & ARCHITECTURAL CONSTRAINTS
==============================================================================

CRITICAL MANDATES FOR ALL AI AGENTS:
1. NO CACHING ALLOWED: The application MUST NOT use caching of any kind whatsoever. All operations must be real-time or completely stateless between executions. Do not implement any memory caches, disk caches, or memoization.
2. *** SINGLE EXE INSTALLER ***: THE COMPILED OUTPUT IN THE .\COMPILED\ FOLDER MUST BE EXACTLY ONE SINGLE CONDENSED `.exe` FILE! IT MUST NEVER BE MULTIPLE FILES! The installer `.exe` internally embeds its entire payload (payload.zip) and ONLY extracts it to the correct persistent paths ONCE IT IS RAN AND INSTALLED!
3. *** ⚠️ PORTRAIT CANVAS TRAP — READ THIS BEFORE ANY PORTRAIT/CROP MATH! *** ⚠️
   The portrait (9:16) conversion does NOT use a simple aspect-ratio crop! It uses the
   "Portrait Canvas Trick" — a multi-stage scale→crop→overlay→compose→pad pipeline that
   can trip up AI agents who assume naive math. If you are writing ANY code that involves
   portrait dimensions, crop regions, FOV guides, overlay positions, or coordinate
   transforms (in the MAIN App, Crop Tools, or anywhere else), you MUST follow these rules:

   ❌ WRONG (common trap): "Portrait 9:16 means clear width = height × 9/16 = 608px for 1080p"
      This assumes a simple center crop at the 9:16 ratio. It is INCORRECT.

   ✅ CORRECT (the actual pipeline): The export scales the source to fill 1280×1920 internal
      space (`force_original_aspect_ratio=increase`), then center-crops to 1280px wide.
      For 1920×1080 input: scale factor = 1920/1080 = 1.778 → 3413×1920 → crop 1280 wide.
      Surviving original horizontal width = 1280 ÷ 1.778 = 720px (NOT 608px).

   THE SINGLE SOURCE OF TRUTH for ALL portrait/crop math is:
     • `src/FortniteVideoSoftware.Core/Media/CoordinateMath.cs` — all coordinate transforms
     • `src/FortniteVideoSoftware.Core/Media/MobileFilterBuilder.cs` — the FFmpeg filter graph
     • `src/FortniteVideoSoftware.Core/Media/CanvasMath.cs` — UI canvas boundary math
   Constants (`CoordinateConstants`): InternalW=1280, InternalH=1920, PortraitW=1080,
   PortraitH=1920, ContentW=1080, ContentH=1620, PaddingTop=150, PaddingBottom=150.
   BackendScale = 1280/1080 = 32/27.

   BEFORE writing or modifying ANY portrait-related math (dimming overlays, FOV guides,
   crop previews, coordinate transforms, overlay placements), ALWAYS verify your formula
   against `CoordinateMath.ScalePlan()` and the scale→crop pipeline in `MobileFilterBuilder`.
   A formula that looks "obviously correct" for 9:16 may be wrong because the internal
   pipeline uses 1280-wide space, not 1080. When in doubt, trace the actual export filter
   graph for a 1920×1080 input and confirm the pixel dimensions match.

1. PROJECT DESCRIPTION & GOALS
------------------------------------------------------------------------------
The Fortnite Video Software project is a robust, hardware-accelerated media
processing suite. Originally written in Python and PyQt5, it suffered from
Global Interpreter Lock (GIL) deadlocks, native C++ binding instability, and
distribution complexities.

The overarching goal of this project is to port the suite into a single,
statically compiled .NET 9 NativeAOT executable. By leveraging C#, Avalonia UI,
and NativeAOT, the software achieves true multi-threading, complete elimination
of GIL limitations, improved IPC safety, and an extremely lightweight, dependency-
free footprint.

2. PRODUCT SPECIFICATIONS & FEATURES
------------------------------------------------------------------------------
* High-Integrity IPC & State Management:
  Configurations and session state are managed through Named System Mutexes
  (`Global\FvsStateTransferMutex`) and write-then-replace atomic JSON handlers.
  Writes strictly target `%PROGRAMDATA%` to adhere to Windows permission models.

* Crash Recovery Protocol (CRP):
  The Bootstrapper uses PID-based file locking (`app_session.lock`) and a 120s
  `safe_mode.sentinel` watchdog to detect unexpected terminations. If a crash
  is detected, it prompts session restoration and prevents crash looping.

* Standalone Installer & Deployment Lifecycle:
  - Payload Extraction: The installer dynamically unpacks `FortniteVideoSoftware.App.payload.zip`
    (which includes native binaries like `libSkiaSharp.dll` and `ffmpeg.exe`) into `%TMP%\Fortnite Video Software`.
  - Elegant Deployment UI: Both installation and uninstallation leverage a beautiful, dark-themed
    Avalonia window (`DeploymentProgressWindow`) to show real-time progress, matching the premium aesthetic.
  - Silent Background Cleanup: When the setup or uninstaller exits, it detaches a background `cmd.exe` process
    to exhaustively wipe all `Fortnite Video Software`, `fvs_*`, and `FVS_*` temp folders from `%TMP%`.
  - Verbose Error Logging: The entire installation lifecycle and any fatal startup exceptions are persistently
    logged directly to `%TMP%\Fortnite_Video_Software.log`. No other traces are left behind.

* MPV Timeline & UI Shell (Avalonia):
  The UI is built with Avalonia (Fluent Themes). It employs a custom `libmpv-2.dll`
  P/Invoke wrapper to handle hardware-accelerated video rendering. To prevent
  deadlocks, timeline scrubbing is debounced at a max of 20fps. A background
  watchdog (`MPVSafetyManager`) monitors the native C++ MPV queue and will
  forcefully reset the internal state machine if a seek request hangs beyond 2.5s.
  The UI enforces strict aesthetics (e.g., 42px bottom navigation buttons, silent
  file deletion without prompts). Auto-exit hooks cleanly shut down the app after
  executing OS actions (e.g., sharing to WhatsApp or opening folders).

* FFmpeg Media Processing Pipeline:
  - Hardware Acceleration Scanner: Tests capabilities using a strict prioritization
    chain (NVIDIA nvenc -> AMD amf -> INTEL qsv -> CPU libx264) with a 15-second
    GPU driver-hang watchdog. Encoder probes must use a real 256x256 yuv420p test
    frame; 128x128 is invalid on current NVENC drivers and causes false CPU fallback.
    Hardware export mode is stored as scanner state (`_hardwareMode`) and must not be
    inferred by parsing the visible `HardwareStatusLabel`; the label is display-only.
    `EncoderManager` treats `GPU`/`AUTO` as first available hardware encoder, not CPU.
  - Encoder Contract: Forces `yuv420p` pixel format and H.264 `Level 4.2` to
    guarantee mobile device playback compatibility.
  - Audio Ducking: 150Hz frequency split (Highpass/Lowpass). High frequencies of
    game audio are sidechain compressed (ducked) against background music.
  - TimeSync Engine: Mathematically shifts gameplay durations to accommodate
    variable-speed scaling without losing alignment with background music.
  - WhatsApp Intro Fix: Prepends exactly 0.1s of the first frame as a static
    lead-in to bypass a known WhatsApp black-screen thumbnail bug.
  - Canvas Math: Applies precision +1px drift correction boundaries (left-edge
    and right-edge specific) to ensure dynamic bounding boxes do not truncate
    under 1080x1920 inverse transformations.

* Single-File Deployment & Build Pipeline:
  Targets `win-x64` using `<PublishAot>true</PublishAot>` and `<TrimMode>full</TrimMode>`.
  Packages all managed code, MSIL, and embedded native libraries into one .exe.
  The production compile entry point is `compile.cmd`, which delegates to `Build.cmd`.
  `Build.cmd` operates without PowerShell UI mutation to ensure the console font
  consistently stays at 16 Consolas.
  Development testing is handled separately by `dev.cmd`:
  - `dev.cmd` starts `dotnet watch run` hot reload for functionality and look/feel checks.
  - `dev.cmd run` launches one Debug app session. (Incremental, fast)
  - `dev.cmd build` performs a fast Debug compile-only check and does not open the app.
  - `dev.cmd restore` refreshes NuGet assets after package/project changes.
  - `dev.cmd clean` securely wipes Debug output (`bin`/`obj`) to guarantee a fresh build.
  Dev commands safely sandbox their execution via `FVS_PROGRAMDATA_ROOT=.dev_data`, ensuring
  local developer tests do not overwrite or corrupt your real production `%PROGRAMDATA%` configs.
  Dev commands target `Debug` + `win-x64` + `--no-self-contained`.
  The app project explicitly includes `**\*.axaml` in `dotnet watch` so UI markup saves
  participate in the hot-reload/watch workflow.

* UI Polish & Interactions:
  - Draggable, interactive START and END timeline markers via precise Canvas hit-testing.
  - Distinct "gentle yellowish" visual feedback overlays for immediate confirmation of button clicks (e.g., SET THUMBNAIL, MARK START).
  - Modern, brightened metallic blue gradients for all primary action buttons.
  - Custom Window Chrome: Custom extended-client-area windows use a shared darker grey brushed-metal chrome. The 30px title bar uses `TitleBarBackground`; the 5px surrounding frame uses `WindowTitleBorder`. Do not hard-code `LightGray` or add per-OS title/frame overrides that bypass these resources.
  - Synchronous Window Bounds tracking via `WindowBoundsHelper.SaveBoundsSync` guarantees that layout, window position, monitor affinity, and sizing are safely committed to disk before the Avalonia application loop terminates.
  - Design System Standards (UX/UI audit baseline):
    * Window Title Standard: All custom title bars use the global `TextBlock.WindowTitleText` style from `AvaloniaApp.axaml`. Window titles are horizontally centered in the 30px title bar across Main, Settings, Music Wizard, Granular Speed Editor, Video Merger, and Crop Tools. Do not locally set left margins on title text.
    * Metallic Chrome Standard: `AvaloniaApp.axaml` owns the shared `TitleBarBackground`, `TitleBarForeground`, and `WindowTitleBorder` resources. The main app title is `Fortnite Video Software` (no `- Pro Edition`). All `MainBorder` 5px frames must bind `BorderBrush="{DynamicResource WindowTitleBorder}"`; all title bars must bind `Background="{DynamicResource TitleBarBackground}"`.
    * Checkbox Standard: All CheckBox controls inherit from a single global style in `AvaloniaApp.axaml` (FontFamily system-default, FontSize 10, Foreground White, Cursor Hand). Hover (`:pointerover`) applies a subtle `#22ffffff` background tint; focus (`:focus`/`:focus-visible`) shows a 2px `#7dd3fc`/`#38bdf8` border ring. This applies app-wide to every checkbox. No CheckBox should set a local `FontSize` override — the global style is the single source of truth.
    * App-Wide Action Button Standard: ALL buttons app-wide (including Main App workflow buttons like PROCESS/CANCEL, dialog actions like APPLY/CANCEL, and wizard steps like PLAY PREVIEW/NEXT) inherit from a single ROOT source of truth in `AvaloniaApp.axaml`. The base `<Style Selector="Button">` enforces a strict universal dimension: `Height="32"` and `FontSize="10"`. Individual buttons may locally override `Width` (e.g., `Width="125"` for PROCESS, `Width="90"` for CANCEL) but MUST NOT hardcode `Height` or `FontSize` in their `.axaml` files. The gigantic buttons of the past (e.g. Height 42, FontSize 12) have been eliminated to ensure consistent scaling and aesthetics across every window. Both rely on the global `Button` style for `CornerRadius="8"`, `FontWeight="SemiBold"`, and `BorderThickness="1,1,1,2"`. The APPLY/PROCESS buttons use the `Success` (green) class; the CANCEL buttons use the `Danger` (red) class.
    * Speed Preset Button Standard: MainWindow and GranularSpeedEditorWindow share global `Button.SpeedPreset`, `Button.BaseSpeedPreset`, and `StackPanel.SpeedPresetRows` styles from `AvaloniaApp.axaml` plus shared wiring in `SpeedPresetButtons.cs`. Preset buttons are `31x25` px with `Padding="0"` so labels never get clipped, the vertical row gap is `3px`, and hover uses a subtle dark amber glow (`#4a3714` background, `#a16207` border, `#fef3c7` text). Both screens use the same two-row quick speed layout: 0.1x, 0.5x, 1.0x, base/default, 1.5x on row 1 and 2.0x, 2.5x, 3.0x, 3.5x, 4.0x on row 2. In Main, the green `BaseSpeedPreset` is always the native default 1.1x. In Granular Speed Editor, the green `BaseSpeedPreset` dynamically reflects the Main screen SPEED value passed into the editor.
    * Slider Thumb Standard: All `Slider` thumbs are globally enlarged to 18×18px resting (was 12px), growing slowly (0.3s `TransformOperationsTransition`) to `scale(1.4)` on hover and `scale(2.0)` when pressed/dragged. The thumb uses a radial gradient (`#7dd3fc` → `#38bdf8` → `#0ea5e9`) on hover. `CompactSlider` class thumbs (timeline scrubber + vertical volume) are 21×21px resting. This standard is defined in `AvaloniaApp.axaml` and applies to every slider app-wide.
     * Volume Slider Standard: The vertical `VolumeSlider` (in MainWindow, flush between the video border and the right pane) uses the PLAIN default Avalonia slider style (matching the Granular Speed horizontal slider), NOT a custom gradient track. It sits inside a slim clear frame: a `Border` `Width="40"` with `Padding="0,8"`, `Background="#15202b"`, `BorderBrush="#475569"`, `BorderThickness="1"`, and `VerticalAlignment="Stretch"` so it anchors to the top and bottom edges of the video player and stretches/shrinks with the app. There is NO horizontal gap on either side — the parent grid `Margin` right edge is `0` (not 16) so the frame touches the right pane, and the video sits flush against its left. To counter vertical track layout drift, its inner Grid is clamped `HorizontalAlignment="Left"` with `Margin="-6,0,0,0"`. The `VolumeBadgeText` ("100%") and speaker icon are colored `#00C870` and shifted `3px` to the right to visually align with the track perfectly.
    * Portrait Dimming (FOV Guide): When Portrait (9:16) mode is enabled, 40% opacity black bands are drawn over the left and right sides of the video to show the crop region. The dimming math EXACTLY matches the export pipeline's "Portrait Canvas Trick" (see `CoordinateMath.cs` + `MobileFilterBuilder.cs`): the export scales source to fill 1280×1920 internal space then center-crops 1280px wide, meaning the surviving horizontal width = `ih × (1280/1920)` = `ih × (2/3)`. The clear center strip is therefore `ih*2/3` and each dim band is `(iw - ih*2/3) / 2` = `iw/2 - ih/3`. Because `MpvVideoView` extends `NativeControlHost` and the native MPV HWND paints over all Avalonia overlays on Windows, this guide is rendered via MPV's own `vf` (video filter) `lavfi=[drawbox...]` chain. The filter is: `lavfi=[drawbox=x=0:y=0:w=iw/2-ih/3:h=ih:color=black@0.4:t=fill,drawbox=x=iw/2+ih/3:y=0:w=iw/2-ih/3:h=ih:color=black@0.4:t=fill]`. For 1920×1080: band_w = 600px, clear center = 720px (exactly matching the 1280/3413.33 scale→crop ratio). The Avalonia `PortraitDimmingGrid` is kept hidden (`IsVisible="False"`, `IsHitTestVisible="False"`) as a structural reference only.
    * Overlay Feedback Bubbles: All Main/Granular tactical feedback uses the shared `FloatingFeedback.Show(...)` Popup animation. MainWindow uses `FeedbackPopup`; Granular Speed Editor uses `GranularFeedbackPopup`. Feedback appears at the bottom-center of the VIDEO area and floats upward while fading out. Because the native MPV HWND (embedded via `--wid`) paints over ALL Avalonia overlays AND suppresses MPV's own OSD layer on Windows, feedback MUST be rendered via an **Avalonia `Popup`**. A `Popup` creates a SEPARATE native popup window (WS_POPUP) with its own z-order that floats ABOVE the embedded MPV HWND. Styling: golden text (`#facc15`) on 50% semi-transparent dark blue (`#0f1b3a`) background. The old bottom-right `ToastHost` feedback path is removed and must not be reintroduced for tactical editor feedback.
    * Music Wizard Toast Layering: `MusicWizardWindow.ShowToast(...)` must set the toast `ZIndex` before adding it to the host panel. The toast ZIndex must be at least 999 and above every existing sibling so it cannot render behind list boxes or content panels.
    * SpinningWheelSlider Tooltips: The `SpinningWheelSlider` custom control suppresses its tooltip during active interaction (drag, wheel scroll, key navigation) to prevent it from destructively popping up over the spinner. The tooltip is saved, cleared during interaction, and restored 1.2 seconds after the last interaction via a cancellable `Task.Delay`.
    * Music Wizard Timeline & Playhead: The wizard timeline uses a dual-marker system: a static dashed gray line for the song start point, and an active smooth-moving red playhead synced at 60fps with the MPV audio preview. Click-to-seek handles instant audio/visual repositioning.
    * NativeControlHost Visibility Bug (MpvVideoView): Avalonia's `NativeControlHost` on Windows has a known bug where setting `IsVisible="False"` on a parent panel does not reliably hide the underlying native HWND. If hidden, the MPV window becomes a persistent invisible click-blocking rectangle. To hide a video view (e.g. navigating back from Phase 3 in the Music Wizard), you MUST completely remove the `MpvVideoView` from the logical tree and call `DisposeMpv()` to forcefully destroy the HWND. It must be dynamically re-instantiated when needed again.
    * Main App Music Overlay: The applied music is drawn on the main timeline as a pink block. The draggable "♫" text-block markers on both ends that glow and cast deep-pink shadows on hover are implemented using **Avalonia `Popup`s**. Because the native MPV HWND paints over all standard Avalonia overlay panels, the markers must be housed in `Popup` controls to guarantee they draw on top of the video player. These dictate `TimelineStartSeconds` and `TimelineEndSeconds`. Advanced pointer handlers enforce strict bounding math: dragging the block or the notes encounters "brick wall" collisions that prevent dragging past the video start/end boundaries, preserving duration exactly without truncation. Arrow keys (`1s` increments) and `Ctrl` + Arrow keys (`50ms` increments) provide extreme granular finessing. Click-focus draws a yellow marching-ants border around the block, which is cleared by clicking elsewhere or hitting Spacebar.
    * Timeline Overlay: The timeline floats at the bottom of the video area on a semi-transparent `#B3000000` strip (height 52px). It includes scale ticks, trim markers, scrub slider, and the pink music overlay block. The music overlay block is drawn last to remain on top and provides grab-handles (🎵) to independently slide the music start, end, and absolute placement. When the user selects a thumbnail frame, `UpdateTimelineMarkers()` draws a persistent yellow camera marker centered on the exact X-axis timeline position.

* Repository & Dependency Architecture:
  - Clean separation from legacy code: All critical FFmpeg and MPV binaries are now hosted independently in a `binaries/` directory and injected at build time.
  - Git LFS Integration (`.gitattributes`): Transparently handles large native binaries (`*.exe`, `*.dll`, `*.com`, `*.zip`) to prevent repository bloat.
  - Intelligent Agent & IDE Exclusions: Employs `.clineignore`, `.agignore`, `.geminiignore`, and `.codexignore` to perfectly optimize AI context windows (excluding `compiled`, `temp_staging`, `.dev_data`, `binaries`, `node_modules`, `dist`, lockfiles, `*.g.cs`) while preserving access to local editor setups.
  - Hardened `.gitignore` safeguards secrets (`.env`, `appsettings.json`), package caches, and test results, while explicitly whitelisting the `binaries/` folder.

==============================================================================
MUSIC WIZARD 3-PHASE ARCHITECTURE
==============================================================================
The Add Music Wizard (MusicWizardWindow.axaml) is strictly divided into 3 sequential phases:
- PHASE 1 (Track Selection): Users select a music track from their local library/files. No playback.
- PHASE 2 (Waveform & Trimming): Users preview the selected MP3 waveform, trim it, and toggle ducking/carving options. Audio preview is active via MpvIpcClient.
- PHASE 3 (Final Review Summary): Side-by-side preview of the original video and the trimmed music. Includes both MpvVideoView (for the video) and MpvIpcClient (for the music), with synchronized playback, waveform timeline, and volume sliders.
- Lifecycle: The 3 phases depend on MusicWizardWindow(string videoPath, double trimStartMs, double trimEndMs) constructor being populated by MainWindow.axaml.cs.

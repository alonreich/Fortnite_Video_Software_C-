1. NO CACHING ALLOWED FOR VIDEO PIPELINES: Do not implement any memory caches, disk caches, or memoization for FFmpeg exports or media generation. (Exception: UI state persistence via JSON and internal libmpv decoding buffers are explicitly allowed and required).
   *** T01 CARVE-OUT (owner-approved, narrow — read before deleting anything) ***
   SINGLE-JOB STAGING FILES INSIDE THE JOB'S OWN TEMP DIRECTORY ARE PERMITTED. The two-pass
   size-targeting route renders the filter graph once into `<tempJobDir>\twopass_master.mp4` and
   points both encoder passes at it (see `Media/TwoPassEncoding.cs`). This is NOT a cache: it is
   created, consumed and deleted within a single export, is never reused across exports, and
   cannot outlive the job folder. The pipeline already stages `core.mp4` the same way.
   THE RULE THAT STILL STANDS: nothing may PERSIST or be REUSED between exports. If a change would
   make a staging file survive a job, keyed on inputs, or shared between runs — that is the caching
   this mandate forbids, and it is not allowed.
   *** PREWARM_01 CARVE-OUT (owner-approved, narrow — read before deleting anything) ***
   THE FILM-LANE PREWARM IS PERMITTED. `Services/FilmstripPrewarm.cs` renders the 60px timeline
   filmstrip in the background the moment MARK START / MARK END are known, so the Granular editor
   and the Voice-Over window usually find it already built. THIS IS NOT THE CACHING THIS MANDATE
   FORBIDS, and the distinction is structural, not a plea:
     - SINGLE ENTRY, MEMORY ONLY. One strip is held in RAM. A new range replaces it. Nothing is
       written to disk and nothing survives the process.
     - TAKE-ONCE. `TryTake` removes the strip as it hands it over, so it can never be served
       twice and two windows can never share (and double-dispose) one bitmap.
     - INPUT-KEYED, SELF-INVALIDATING. Keyed on (path, start, duration, frames). Any trim change
       or a different video makes the held strip unreachable and cancels the render in flight.
     - NOT ON THE EXPORT PATH. It produces a UI decoration. No exported frame, encoder decision
       or timing calculation reads it. If it is empty, stale or never runs, the only consequence
       is that a lane renders on demand exactly as it did before.
   It is the SAME single render the screen would have started itself, moved earlier in time — the
   opposite of a result outliving its job, which is what the mandate exists to prevent.
   THE RULE THAT STILL STANDS: if a change would make it PERSIST to disk, be REUSED across
   exports, or feed anything that reaches the output file, it stops being a prewarm and becomes
   the caching this mandate forbids. A persistent thumbnail cache remains NOT permitted.

3. *** ⚠️ PORTRAIT CANVAS TRAP ⚠️ ***
   The portrait (9:16) conversion does NOT use a simple center crop!
   It uses the "Portrait Canvas Trick": scale -> crop -> overlay -> compose -> pad.
   - For 1920x1080 input: scale factor = 1920/1080 = 1.778 -> 3414x1920.
     ⚠️ IT IS 3414, NOT 3413. The exact product is 1920 x 16/9 = 3413.33, and `CoordinateMath
     .ScalePlan` applies `EvenUp(FracCeil(...))` -> ceil to 3414 -> already even -> 3414. The
     round-UP-then-EVEN-UP order is mandatory: video dimensions in yuv420p MUST be even, so 3413
     is not a legal width and never was. A real export confirms it (`scale=3414:1920` in the
     FFmpeg filter graph). This line previously said 3413; anyone "correcting" the code to match
     that would produce an odd width and break the filter graph. DO NOT.
   - Then it center-crops to exactly 1280px wide (Internal Space).
   - Surviving original horizontal width = 1280 / 1.778 = 720px (NOT 608px).
   THE SINGLE SOURCE OF TRUTH for all portrait math is:
   `src/FortniteVideoSoftware.Core/Media/CoordinateMath.cs`
4. *** ⚠️⚠️ TWO SEPARATE VIDEO-PREVIEW RENDER PATHS — NEVER LET THEM BLEED INTO EACH OTHER ⚠️⚠️ ***
   The app has EXACTLY TWO, mutually-exclusive, code-isolated preview render paths. They are
   chosen ONCE at startup and a given machine only ever runs ONE of them:

     PATH A — GPU ZERO-COPY (the DEFAULT, the ONLY path for machines WITH a real GPU):
       Governed by Section 1 "THE 7 BIBLICAL NORTHSTAR KEYPOINTS" and Section 5 (the VRAM
       journey). This is SACRED, hand-crafted, GPU-only, Windows-only. It is the reason the app
       exists at this quality. Selected when `VideoRenderMode.UseHardwareAcceleration == true`
       (a real NVIDIA/AMD/Intel adapter is present AND WGL_NV_DX_interop initializes).

     PATH B — CPU SOFTWARE FALLBACK (ONLY for machines with NO real GPU: VMs, RDP-blocked GPU,
       headless/basic-display). Governed by Section 5B. Uses mpv's "sw" render API into a
       WriteableBitmap. Selected ONLY when `UseHardwareAcceleration == false` OR the GPU WGL
       bridge physically throws.

   HARD RULES FOR ALL AI AGENTS AND HUMANS (violating ANY of these is a regression):
   (R1) You may NEVER modify, "optimize", simplify, or "unify" Section 1's 7 keypoints or the

        A duplicate override BREAKS COMPILATION and strands the GPU composition-surface sizing
        (keypoint #2). This exact mistake was made once and reverted — do not repeat it.
   (R4) `vo=libmpv` and `hwdec=cuda,dxva2,auto-safe` on the GPU path are UNCHANGED and mandatory
        (keypoint #3). The CPU path sets `hwdec=no`. Do not cross-wire these.
   (R5) If you are "fixing the CPU preview" and find yourself editing anything in Section 1 /

   (R6) ⚠️ NO UNBOUNDED WAIT MAY EVER CROSS BETWEEN THE RENDER THREAD AND THE UI THREAD, IN EITHER

        `UpdateSurface`; `Dispose` runs on the UI thread and needs that same lock. So a blocking

        context rather than blocking. Do not replace either with `Invoke`, `.Result`, `.Wait()`
        with no timeout, or a bare `lock` — whatever the syntax, an unbounded wait here freezes
        the entire application with no error and no recovery.

1. THE 7 BIBLICAL NORTHSTAR ARCHITECTURE KEYPOINTS
------------------------------------------------------------------------------
>>> SCOPE: This section describes PATH A (GPU zero-copy) ONLY. It is SACRED and applies to
>>> machines WITH a real GPU. It must NEVER be altered to accommodate the CPU fallback (PATH B,
>>> Section 5B). See the "TWO SEPARATE VIDEO-PREVIEW RENDER PATHS" mandate above. <<<
Our goal is maximum GPU utilization and Zero-Copy UI integration on a C# .NET 9 NativeAOT footprint.
1. Zero-Copy Memory: Maintained. WGL_NV_DX_interop2 aliases the texture natively in the driver. Pixels never traverse the PCIe bus to the CPU.
2. Native UI Composition: Maintained. The extracted IDXGIResource.SharedHandle feeds directly into Avalonia's CompositionDrawingSurface (UpdateWithKeyedMutexAsync), preserving exact Z-index overlay rendering. No NativeControlHost/HWND hacks!
3. Maximum GPU Utilization: ⚠️ COMPROMISED BY DESIGN ⚠️.
   CRITICAL AI WARNING: DO NOT TRY TO "FIX" THIS TO `d3d11va`.
   Because libmpv strictly requires an OpenGL render API, and Avalonia strictly requires a D3D11 surface, we use `WGL_NV_DX_interop2`. Native `d3d11va` hardware decoders CANNOT initialize inside an OpenGL context without falling back to CPU software decoding.
   The mandatory fix is `hwdec=cuda,dxva2,auto-safe`. The GPU uses a microscopic "translation tax" (CUDA/DXVA2 -> OpenGL -> D3D11) completely in VRAM. It is the ONLY way to retain hardware acceleration. DO NOT OUTSMART THIS.
4. The Hybrid Graphics Compromise (Optimus / Switchable GPUs): Resolved. WGL-to-DX interop successfully bridges the libmpv OpenGL limitation while keeping the D3D11 surface intact for Avalonia.
   CRITICAL AI NOTE: On laptops with dedicated GPUs (e.g. RTX 4070) alongside integrated Intel CPUs, Windows OS power management routinely attempts to route D3D11 to NVIDIA and OpenGL to Intel. Because WGL_NV_DX_interop physically cannot bridge two different chips, this causes a "black screen" crash.
   The mandatory fix implemented is exporting `NvOptimusEnablement` and `AmdPowerXpressRequestHighPerformance` in the NativeAOT `Program.cs`. This forces the driver to hijack the entire process onto the high-performance GPU, preserving the zero-copy bridge. Pure Intel integrated GPUs physically lack this extension and will inevitably fall back.
5. NativeAOT Compilation: Maintained. Uses native Windows opengl32.dll and D3D11 libraries via [LibraryImport] and [UnmanagedCallersOnly]. No ANGLE/GStreamer bloat.
6. Front-End Editing: Maintained. The UI retains libmpv, preserving advanced caching and frame-accurate scrubbing for the timeline.
7. Back-End Exporting: Maintained. The FFmpeg headless encoding pipeline remains completely isolated from the UI render loop.
   >>> THE EXPORT BACKEND IS FULLY DOCUMENTED IN SECTION 5C. If you are touching encoder selection,
   >>> `-hwaccel`, rate control, two-pass, the size-target retry, or the export filter graph, READ
   >>> SECTION 5C FIRST — it exists because every rule in it was once broken in shipped code.
   >>> Note the scope split: Sections 1/5/5B are the PREVIEW (libmpv). Section 5C is the EXPORT
   >>> (ffmpeg.exe). They share no code and no decisions; never justify a change in one by the other.

2. THE THREE (3) SUB-APPLICATIONS
------------------------------------------------------------------------------
The software suite comprises 3 completely separate processes to ensure strict memory isolation:
1. MAIN App: The primary application (`MainWindow.axaml`). Handles timeline, trimming, music wizard, and final export.
2. Video Merger: Joins separate videos via FFmpeg (`VideoMergerWindow.axaml`). Opened as a separate process. Its encode backend is `MergerWorker.cs` and follows Section 5C exactly like the Main App (hardware decode per input, encoder override, and two-pass at 100% "Lossless" only).
3. Crop Tools: Precision canvas interface (`CropToolWindow.axaml`) to export the JSON config file that powers Portrait mode coordinates. Opened as a separate process. It NEVER encodes video — `ffprobe` for metadata and SkiaSharp for PNGs only — so NOTHING in Section 5C applies to it.
AI NOTE: Do not convert Merger or Crop Tools to modal dialogs. They intentionally run as separate executables and instantly close the Main App.

      temp/staging: %TMP%\Fortnite_Video_Software_DEV
      dev logs   : %TMP%\Fortnite_Video_Software_DEV           (`FVS_DEV_LOG_DIR`, dev.cmd line 25)
  UNDER THAT ROOT, whichever it is:
      settings.json · session_state.json · recovery_v2.json · app_session.lock ·
      safe_mode.sentinel · clean_shutdown.intent · crops_coordinations.conf ·
      logs\ · uistate\   (uistate = the ISSUE_09 home for onboarding counters and dismissed hints)
  ⚠️ `%APPDATA%\FortniteVideoSoftware\Settings` IS LEGACY AND MUST NEVER BE WRITTEN TO. It was the
  third state root ISSUE_09 removed; `ApplicationPaths.LegacyRoamingUiStateDirectory` exists ONLY so
  `UiStateStore.MigrateLegacyFilesOnce()` can move old installs across. Any documentation or code
  that names it as a live location is describing the pre-ISSUE_09 world and is wrong.
  ⚠️ DO NOT INVENT A FOURTH ROOT. The installer's preserve-settings switch and the uninstaller's

- Logging: Use `RuntimeLog` (shared by all 3 apps; the Core project's `CoreLogger` forwards Info/Fail/Debug/Append to it via delegates wired in `Program.cs`). Dev runs write strictly to `%TMP%\Fortnite_Video_Software_DEV\`. The single active log is capped at 10 MB and rotates BEFORE a batch would exceed the cap; rotated `.old` files use a millisecond+GUID name (collision-proof across the 3 concurrent processes) and are pruned by count (5), total size (~50 MB) AND age (14 days). All processes serialize writes through the `Global\FortniteVideoSoftwareLogMutex` on a shared-append handle, and the bounded 10k queue drops-with-warning under saturation rather than growing memory. Full FFmpeg/FFprobe commands and full file paths log at DEBUG (dev-only) so the production log never exposes user paths; INFO keeps a safe trail (encoder/mode, file names, exit codes, GPU discovery, cancellation). The live `LogAppended` callback is exception-guarded so a faulty on-screen log viewer cannot disturb the writer.

  *** LOGGING INVARIANTS — AI AGENTS: DO NOT REGRESS THESE (audit round 7 fixed all seven) ***
  Every rule below exists because the opposite was once true in shipped code. If a change you are
  making requires breaking one of them, you are editing the wrong layer.
  (L1) THE 10 MB CAP IS ENFORCED IN THREE PLACES, NOT ONE. `RuntimeLog.SafeWrite` truncates any
       SINGLE entry over `MaxSingleEntryBytes` (64 KB) with an explicit "[truncated N bytes]"
       marker; the drain loop in `ProcessLogQueue` stops at `MaxBatchBytes` (1 MB) per batch; the
       post-write burst loop stops the moment `_estimatedSize` reaches `MaxLogSize`. Removing ANY
       of the three makes the cap unenforceable again — the old code drained all 10,000 queued
       entries into one StringBuilder and then appended 500 more AFTER the size check.
  (L2) NOTHING OUTSIDE `RuntimeLog` MAY OPEN THE LOG FILE. `DeploymentFootprint.InstallReportPath`
       is the SAME file `RuntimeLog.LogPath` returns when the app is not running from the install
       directory. `DeploymentReporter` used to `File.WriteAllText`/`AppendAllText` it directly with
       no mutex, no cap and no try/catch — racing RuntimeLog's writer, breaking rotation, and
       truncating the user's whole log up to five times per install run. It now routes through
       `RuntimeLog.AppendRaw`. Any new installer/updater/diagnostic writer must do the same.
  (L3) LOGGING MUST NEVER THROW INTO A CALLER. `AppendFatalAsync` is invoked from inside catch
       blocks in `DeploymentLifecycle`; a throwing logger there kills the installer while it is
       reporting a failure. Keep every write path non-throwing.
  (L4) RETENTION RUNS AT STARTUP, NOT ONLY AT ROTATION. `CleanupOldLogs` is called once from
       `ProcessLogQueue` before the consuming loop AND from the rotation branch. Rotation-only
       cleanup meant a machine whose log never hit 10 MB never enforced the age/size rules at all.
  (L5) THE RETENTION SWEEP COVERS THE AUXILIARY FILES TOO — `mpv_debug_*.log`,
       `<log>.crash.<pid>.log` (EmergencyWrite when the mutex is unavailable) and
       `<log>.<pid>.local.log` (mutex creation failure). The count rule (`MaxOldLogs` = 5) applies
       ONLY to rotated `.old` files so dev mpv logs cannot evict real rotation history; size and age
       apply to everything. Do not reintroduce the undocumented `MaxOldLogs * 2`.
  (L6) SILENT LOG DEATH IS A BUG. A failed batch increments `_failedBatchCount` and the next
       successful write reports the loss as `[WARN] LOGGER`. A log that simply stops updating must
       never be indistinguishable from a clean run.
  (L7) `LogAppended` IS A STATIC EVENT AND ITS HANDLERS RUN SYNCHRONOUSLY ON THE CALLER'S THREAD.
       Handlers must be cheap, must bound whatever they buffer, and must NEVER log — that recurses.
       `PhaseOverlayControl` caps its hand-off queue at 500 and unsubscribes in BOTH `StopOverlay`
       and `OnDetachedFromVisualTree`, because a window closed mid-export otherwise strands the
       subscription and keeps the control alive for the session.
  (L8) LEVEL DISCIPLINE IS A PRIVACY CONTRACT, NOT A STYLE CHOICE. Full file paths, full
       FFmpeg/FFprobe command lines and full exception stacks are DEBUG (dev-only). INFO carries
       `Path.GetFileName` only. Never promote a path or a command line to INFO/FAIL "for
       convenience" — production logs are attached to bug reports.

5. HARDWARE RENDERING PIPELINE (THE ZERO-COPY VRAM PATH)
------------------------------------------------------------------------------
>>> PATH SELECTION IS SUITE-WIDE AND CACHED. `VideoRenderMode.Initialize()` is called by
>>> `AvaloniaApp.OnFrameworkInitializationCompleted` in EVERY process (Main App, Video Merger,
>>> Crop Tools), so all three choose PATH A / PATH B through the same one method — there is no
>>> per-app variant. Since DOC_AUDIT_02 it reads the answer the first app published
>>> (`Media/HardwareCapability.cs`, Section 5C.0) instead of re-running the D3D11/DXGI probe.
>>> ⚠️ The cache is keyed on the WINDOWS SESSION + remote flag, because Windows blocks the GPU
>>> inside RDP — crossing that boundary always re-probes. Any cache problem falls through to a
>>> real probe, so this can never downgrade a machine. <<<
To fully understand the architecture (and the Keypoint 3 translation tax), this is the exact journey of a single video frame. The frame NEVER touches the CPU (RAM) after being read from disk; it stays entirely in GPU VRAM.

.mp4 Video File (Disk)
  ===> libmpv Demuxer (CPU/RAM parsing only)
  ===> NVIDIA/AMD Hardware Decoder (VRAM via hwdec=cuda/dxva2)  [The Translation Tax Origin]
  ===> OpenGL Framebuffer Object [FBO] (VRAM via mpv_render_context)
  ===> WGL_NV_DX_interop2 Bridge (VRAM cross-API translation)
  ===> D3D11 Shared Texture (VRAM)
  ===> IDXGIKeyedMutex (VRAM sync lock, producer/consumer handshake)
  ===> Avalonia CompositionDrawingSurface (VRAM)
  ===> The End User's Display Monitor (GPU Swapchain)

5B. CPU / RDP SOFTWARE PREVIEW FALLBACK (THE NON-GPU PATH == "PATH B")
------------------------------------------------------------------------------
>>> This is PATH B. It is a COMPLETELY SEPARATE, code-isolated path from PATH A (the GPU
>>> zero-copy pipeline in Sections 1 & 5). See the top-of-file mandate "TWO SEPARATE
>>> VIDEO-PREVIEW RENDER PATHS" for the hard rules (R1–R5). <<<
⚠️ SCOPE GUARD FOR AI AGENTS: This section documents ONLY the software fallback. It does
NOT modify, replace, or relax the 7 Biblical NorthStar keypoints (Section 1) or the Zero-Copy
VRAM path (Section 5) — those remain the mandatory, hand-crafted GPU-only architecture for
Windows. The fallback is a SEPARATE, additive path that runs ONLY when the GPU bridge is
physically impossible. GPU machines NEVER execute a single line of it. If editing this fallback
ever requires you to change anything in Section 1 or Section 5, you are doing it wrong — stop.

WHY IT EXISTS (root cause): the entire zero-copy preview requires the `WGL_NV_DX_interop2`
bridge, which needs a real GPU whose OpenGL driver exports the `WGL_NV_DX_interop` extension.
On (a) machines with NO dedicated/compatible GPU (pure software/basic-display adapters), or
(b) RDP sessions where Windows blocks the GPU, that extension is absent and
`InitializeWGLInteropContext()` throws `WGL_NV_DX_interop not supported by the OpenGL driver`.
BEFORE this fallback existed, `vo` was set to `null` in CPU mode and the preview showed only
the "Preview unavailable" overlay — there was NO way to see video on those machines (export
still worked via FFmpeg's CPU encoder; only the live PREVIEW was missing).

THE FRAME JOURNEY (software path — the frame IS read back to CPU/RAM, unlike the VRAM path):
.mp4 Video File (Disk)
  ===> libmpv Demuxer (CPU/RAM)
  ===> CPU Software Decoder (hwdec=no — no hardware decode on this path)
  ===> mpv Software Render API (render context api_type="sw")
  ===> `mpv_render_context_render` into a managed byte[] buffer (SW format "bgr0", stride=w*4)
  ===> alpha byte forced to 255 (bgr0 leaves X=0 which Bgra8888 treats as transparent)
  ===> Avalonia WriteableBitmap (Bgra8888, AlphaFormat.Opaque)
  ===> MpvVideoView.Render(DrawingContext) paints it letterboxed (aspect-fit)
  ===> The End User's Display Monitor (normal Avalonia compositor)

IMPLEMENTATION (`MpvVideoView.cs` + `LibMpvInterop.cs`):
- `vo=libmpv` is now set for BOTH paths (was `null` for CPU); the render API — OpenGL on the
  GPU path, "sw" on the CPU path — drives it. `hwdec` stays `cuda,dxva2,auto-safe` on GPU and
  `no` on CPU.
- Path selection in `InitializeMpv()`: (1) if the boot GPU probe reports no hardware accel ->
  go straight to `InitializeSoftwareRender()`. (2) if it reports hardware accel but
  `InitializeWGLInteropContext()` THROWS (the RDP/no-extension case) -> release the half-built
  GPU interop resources, then fall back to `InitializeSoftwareRender()`.
- ROOT-CAUSE PROBE FIX (`GpuCapabilityProbe.HasRealGpuAdapter()`): a D3D11 device can be created
  on WARP / "Microsoft Basic Render Driver" / "Microsoft Hyper-V Video" with NO real GPU — it
  reports Feature Level 11 yet has no OpenGL WGL interop, which previously made the probe log
  "Hardware acceleration enabled" and take the GPU path (only reaching software via the WGL
  exception). The probe now enumerates DXGI adapters and requires a REAL GPU vendor
  (NVIDIA 0x10DE / AMD 0x1002,0x1022 / Intel 0x8086, and NOT the DXGI software flag); if only a
  Microsoft software/basic/Hyper-V adapter is present it reports `UseHardwareAcceleration=false`,
  so a GPU-less/VM box deterministically takes the CPU path (`hwdec=no` + sw render) from the
  start. Any enumeration failure returns "assume GPU" so real machines are never downgraded.
- `InitializeSoftwareRender()` creates a render context with `MPV_RENDER_PARAM_API_TYPE="sw"`,
  registers the same frame-ready update callback, and starts a dedicated background thread
  (`MpvSwRenderThread`) that waits on the shared render signal.
- Per frame (`SoftwareRenderOnce`): renders to the CONTROL's OWN pixel size (captured in
  `ArrangeOverride`), NOT the decoded video size. ⚠️ CRITICAL: with `vo=libmpv`, mpv only
  outputs/advances VIDEO frames while the client is actively calling `mpv_render_context_render`.
  Gating the render loop on `MpvIpcClient.VideoWidth>1` deadlocks (no render -> no frame -> width
  stays 0 -> no render), which manifests as "audio plays but no picture". Rendering to the control
  size (mpv scales + letterboxes the video into it, keepaspect=yes, black bars) breaks the
  deadlock. `ArrangeOverride` also re-signals the render thread on resize so the first/paused
  frame paints. It (re)allocates the CPU buffer and renders via the four SW params — SW_SIZE(16, int[2]),
  SW_FORMAT(17, "bgr0"), SW_STRIDE(18, size_t=w*4), SW_POINTER(19, pinned buffer) — forces the
  opaque alpha, then posts `PushSoftwareFrame` to the UI thread which copies into the
  `WriteableBitmap` under a lock and calls `InvalidateVisual()`.
- `Render()` override: in software mode it draws the bitmap aspect-fit/letterboxed; otherwise
  it defers to the base (GPU composition) path.
- Cleanup (`Dispose`): stops the SW thread (join 500ms), disposes the bitmap/buffer, frees the
  render context (guarded so the GL-context `wglMakeCurrent` is skipped when `_hglrc==0`).

FAIL-SAFE CONTRACT (do not weaken): the software path is wrapped so that ANY failure
(context create, render error, exception) simply leaves `IsSoftwareFallbackActive=true` — i.e.
the original "Preview unavailable" overlay — so it can NEVER be worse than before and can NEVER
crash or perturb the GPU pipeline. RDP note: the RDP-detection guardrail UI ("RDP SESSION" /
"RDP: CPU BLOCKED", Section 10) is unaffected and still informs the user their GPU is blocked;
the software preview just means they now also see the video while in that state.
NATIVE-ABI CAVEAT: the SW render param enum values (SW_SIZE=16, SW_FORMAT=17, SW_STRIDE=18,
SW_POINTER=19) and the "bgr0" pixel format are mpv-native — changes here MUST be verified on an
actual CPU-only or RDP target, not just by static review.

------------------------------------------------------------------------------
5C.0 — ONE PROBE FOR THE WHOLE SUITE (`Media/HardwareCapability.cs`)
------------------------------------------------------------------------------
The suite is THREE separate processes (Section 2). They must reach IDENTICAL conclusions about the
machine, and they must not each pay to find out.

  MAIN APP AT BOOT (the only scanner in the suite)
        │  HardwareScanner.ScanSharedAsync(ffmpeg)   → "which chip ENCODES"
        │  VideoRenderMode.Initialize()              → "which path PREVIEWS"
        ↓  publishes both to…
  ProgramData\uistate\hardware_capability.json      (via UiStateStore, per ISSUE_09)
        ↓  read by…
  VIDEO MERGER + CROP TOOLS + every later Main App launch — NO re-scan, NO second opinion.

WHAT THIS REPLACED: `VideoRenderMode.Initialize()` ran the D3D11/DXGI probe in EVERY process, and
the encoder question was worse than duplicated — it was INCONSISTENT. The Merger ignored the boot
scan AND the user's Settings choice and hardcoded the literal string "GPU", so the two apps could
legitimately pick different encoders on the same machine. A full `HardwareScanner.ScanAsync` also
spawns ffmpeg.exe up to FOUR times (one `-hwaccels` listing plus one real trial encode per vendor).

THE TWO HALVES ARE VALIDATED SEPARATELY, because they go stale for different reasons:
  ENCODER half invalidated by → a different ffmpeg.exe (path + byte-length + last-write
                                fingerprint, so an app update re-probes by itself), age > 7 days
                                (covers a driver install), or a recorded SCAN_FAILED.
  RENDER  half invalidated by → a different WINDOWS SESSION. ⚠️ THIS IS THE RDP GUARD AND IT IS
                                LOAD-BEARING: Windows blocks the GPU inside a remote session, so a
                                result recorded locally is actively WRONG under RDP and vice-versa.
                                The session id AND the remote-session flag are both in the key.

⚠️ A FAILED SCAN IS NEVER PUBLISHED. Caching "we could not tell" would freeze a broken state across
all three apps — exactly the G01/G02/G03 failure mode, but suite-wide and persistent.

FAIL-SAFE: every read returns null on ANY problem and every write is non-throwing. An unreadable
cache simply means the caller probes for itself — the original behaviour. This can never make the
suite worse than not having it.

5C.1 — WHICH CHIP ENCODES (THE SELECTION CHAIN)
------------------------------------------------------------------------------
ONE resolver serves every application: `ExportEncoderStrategy.Resolve(override, bootScan, ffmpeg)`.

  1. Settings ▸ Performance override   (AppSettings.VideoEncoderOverride)
        ↓  "Auto"/empty falls through to…
  2. This process's OWN boot scan       (Main App only — Merger and Crop Tools pass null)
        ↓  null / SCAN_FAILED falls through to…
  3. The suite-wide published result    (HardwareCapability — see 5C.0)
        ↓  nothing known →
  4. "SCAN_FAILED"  ⚠️ NOT "CPU". EncoderManager treats it as "unknown, re-probe at export time".

  resolved strategy → ProcessWorker.HardwareStrategy / MergerWorker.HardwareStrategy
        ↓ resolved by…
  EncoderManager  →  h264_nvenc | h264_amf | h264_qsv | libx264

⚠️ AN APP MUST NEVER BUILD ITS OWN STRATEGY STRING. The Main App reaches this resolver through
`MainWindow.ResolveHardwareMode()` → `ExportPayload.HardwareMode` → `MainMediaController`; the
Merger calls the resolver directly in `VideoMergerWindow` because it has no ExportPayload. Both
end at the SAME function. Adding a new export surface? Call `ExportEncoderStrategy.Resolve`.
(`MergerWorker.HardwareStrategy` still defaults to the legacy "GPU" so an un-set caller behaves
sanely, but that is a safety net, NOT the path the UI takes.)

THREE OUTCOMES OF THE BOOT SCAN — they are NOT interchangeable:
  "NVIDIA"/"AMD"/"INTEL"  a probe RAN and PASSED. Use that encoder.
  "CPU"                   every probe RAN and every probe FAILED. Genuinely CPU-only.
  "SCAN_FAILED"           the scan ABORTED (exception/timeout). Capability UNKNOWN.
                          EncoderManager re-probes and RECOVERS to hardware if it finds any.

⚠️ WHY THE SENTINEL EXISTS (G01/G02/G03 — this cost every user their GPU): a crash in
`ChildProcessTracker`'s static initializer aborted the scan, which returned "CPU", which set
`EncoderManager.ForcedCpu=true`, which made it DISCARD its own successful encoder probe. The dev
log showed "Found Hardware Encoders: h264_amf, h264_nvenc, h264_qsv" immediately followed by
"Forced CPU selected. Using libx264" — on a machine with an RTX. NEVER collapse "SCAN_FAILED" back
into "CPU". `MainWindow._hardwareMode` also DEFAULTS to the sentinel: "not scanned yet" is not
"CPU-only".

------------------------------------------------------------------------------
5C.2 — DECODING: `-hwaccel` IS A PER-INPUT OPTION
------------------------------------------------------------------------------
`EncoderManager.GetDecodeFlags(encoder)` returns the decode flags for the CURRENT encoder
(cuda / d3d11va / qsv / none). It MUST be emitted immediately before EVERY VIDEO `-i`.

⚠️ `-hwaccel` binds ONLY to the next `-i`. Emitting it once at the head of the command line — which
is what the code did before G04 — leaves every additional video input decoding in SOFTWARE: the
thumbnail-intro clone (the same file re-opened) and any video meme, on every export, on every GPU
machine. The Merger (G08) had no `-hwaccel` at all, so its clips were 100% software-decoded.

Image inputs (text overlay PNG, image memes) and audio-only inputs deliberately get NO decode
flags — there is no hardware path for a looped still, and adding it only makes FFmpeg warn.

⚠️⚠️ DO NOT ADD `-hwaccel_output_format` (ISSUE_01). It leaves decoded frames in VRAM, and the
export filter graph is 100% software with no `hwdownload` anywhere — FFmpeg aborts before a single
frame, the encoder-fallback loop silently drops to libx264, and the UI claims otherwise. Plain
`-hwaccel` returns frames to system memory automatically, which is what this graph requires.

G07 — WHY A TRUE VRAM-RESIDENT EXPORT IS NOT AVAILABLE.
⚠️ THE FULL FINDING LIVES IN SECTION 8 AND NOWHERE ELSE. READ IT THERE BEFORE ACTING.
A duplicate of this analysis used to sit here and a third copy sat in the Section 9 changelog. The
copies DISAGREED — this one listed four missing filters and proposed emulating `pad`; Section 8
lists a fifth blocker the others missed (`scale_cuda` in the shipped build has no crop options),
records that the "pad_cuda does not exist upstream" claim was FALSE, and concludes the honest
blocker count is TWO (`fade`, `cas`) if the ffmpeg build is also replaced. Maintaining one finding
in three places is what let them drift, so only Section 8's version survives.
THE OPERATIONAL RULE THIS SECTION NEEDS: the export frame journey is NVDEC(VRAM) → PCIe download →
software filters → PCIe upload → NVENC, and that is CORRECT, not an oversight. Omitting
`-hwaccel_output_format` is the mechanism that performs the download. Do not add it.

5C.3 — RATE CONTROL: TWO MODES, AND THEY BEHAVE COMPLETELY DIFFERENTLY
------------------------------------------------------------------------------
| Mode          | Main App                | Merger        | Flags                | Two-pass? |
|---------------|-------------------------|---------------|----------------------|-----------|
| SIZE-LOCKED   | MB quality slider       | 100% Lossless | -b:v / CBR / VBR     | YES       |
| QUALITY-LOCKED| "ORIGINAL QUALITY"      | below 100%    | -crf / -cq / -qp     | NO        |

The distinction is the single most important thing in this section. Two-pass REDISTRIBUTES A FIXED
BUDGET. CRF/CQ is constant-quality and has NO budget, so a second pass there costs time and changes
nothing measurable. Do not "enable it everywhere for better quality" — that is a misunderstanding
of what it does.

NVENC SETTINGS ARE OWNER-LOCKED (G06, reviewed and deliberately declined):
`-preset p7 -multipass fullres -rc-lookahead 32 -spatial-aq 1 -temporal-aq 1 -bf 2 -b_ref_mode
middle`. This is the SLOWEST NVENC configuration available and dropping to p5/p6 + `-multipass
qres` would be several times faster — the owner has explicitly chosen maximum quality. DO NOT
change these values.

------------------------------------------------------------------------------
5C.4 — TWO-PASS SIZE TARGETING (T01) — `Media/TwoPassEncoding.cs`
------------------------------------------------------------------------------
WHAT IT IS: pass 1 encodes the whole timeline and writes a per-frame COMPLEXITY MAP; pass 2 reads
that map and spends the SAME total budget where it is actually needed — taking bits from a static
lobby and giving them to a firefight.

WHAT IT IS NOT — three things it is constantly confused with:
  `-rc-lookahead 32`  peeks ~32 frames (half a second at 60fps). CANNOT trade across a clip.
                      Already enabled on NVENC. Different feature.
  `-multipass fullres` NVENC encodes each FRAME twice for better in-frame quantization.
                      Already enabled on NVENC. Different feature.
  Any pixel filter    Two-pass touches NO pixels. No blur, no smoothing, no filter changes,
                      no motion interpolation. ONLY bit allocation differs.

GATED THREE WAYS — all three are load-bearing:
  (1) A BITRATE BUDGET MUST EXIST — see 5C.3. Never on CRF/CQ.
  (2) libx264 ONLY. ⚠️ `h264_nvenc` does NOT implement libavcodec's stats-file two-pass. It
      ACCEPTS `-pass` and SILENTLY IGNORES IT, which is worse than not offering the feature at
      all — you would ship a doubled encode time with zero benefit and no error. Do not wire this
      into the NVENC/AMF/QSV paths.
  (3) Not already failed this job (`twoPassDisabled`).
Any other combination takes the original single-pass path, byte-identical to before.

TWO ROUTES:
  FAST (default) — the filter graph (14-18 way split, lanczos portrait scale, zoom pads, HUD
    overlays) DOMINATES wall clock, so a naive `-pass 1`/`-pass 2` re-runs it twice and costs ~2x.
    Instead the graph runs ONCE into a near-lossless CRF 14 master and both passes read that file.
      Stage 1  filter graph ──► <tempJobDir>\twopass_master.mp4   (progress 0-60% of the band)
      Pass 1   master ──► complexity map, -f null NUL             (60-75%)
      Pass 2   master ──► core.mp4, -c:a copy                     (75-100%)
    ⚠️ THE MAIN APP AND THE MERGER USE THESE EXACT SAME BOUNDARIES ON PURPOSE
    (`ProcessWorker.TwoPassGraphFraction`/`TwoPassAnalysisFraction` = 0.60/0.75, and the literal
    60/75 in `MergerWorker.RunTwoPassTailAsync`; the SLOW route splits at 0.45 in both). They
    drifted apart once — the Merger was on 60/78 — which silently made this documentation wrong
    for one of the two apps. If you retune one, retune the other AND this block, together.
    Cost ~1.3-1.4x one render. Audio is FINALISED in the master and stream-copied by pass 2, so it
    is encoded exactly ONCE across the export — no second-generation loss.
  SLOW — chosen automatically when `DiskSpaceGuard.HasRoomFor` reports the staging drive cannot
    hold the master. The graph genuinely runs twice (~2x) rather than abandoning the accurate size
    targeting the user asked for. `HasRoomFor` is NON-FATAL by design (unlike `DiskSpaceGuard
    .Check`) and returns true on any probe error, so an unmeasurable machine is never downgraded.

⚠️⚠️ THE SLOW ROUTE'S PASS 1 MUST MAP **AND ENCODE** THE AUDIO BRANCH.
The obvious optimisation is `-an`, since audio contributes nothing to a video complexity map. IT
DOES NOT WORK. With `-filter_complex`, a labeled output that nothing consumes makes FFmpeg abort
with an unconnected-output error — and `-map [a] -an` is the same thing by another route. Both
slow passes map video AND audio; the null muxer discards them, and the audio chain is trivial next
to the video graph. ONLY the FAST route's pass 1 may use `-an`, because it reads a plain FILE
rather than a filter graph. This distinction is not cosmetic; getting it wrong is a hard failure at
runtime that no static review catches.

⚠️ BOTH PASSES MUST USE IDENTICAL ENCODER SETTINGS apart from the pass number — x264 validates the
stats file against them and a mismatch either aborts pass 2 or silently degrades it.
`TwoPassEncoding.PassArgs()` is the SINGLE source for both, so they cannot drift. Do not inline
pass flags at a call site.

⚠️ STATS HYGIENE: x264 writes BOTH `<prefix>-0.log` AND `<prefix>-0.log.mbtree`.
`TwoPassEncoding.Cleanup()` runs BEFORE each attempt as well as after, because a stale stats file
would hand pass 2 a complexity map built for a different bitrate or a different video — silent
quality damage with no error anywhere. Keep the before-call.

FAILURE IS NEVER FATAL: if either pass fails, two-pass is disabled for the rest of the job and the
ordinary single-pass encode runs instead. The user always gets a video. The disable flag also
guarantees the retry cannot loop.

PROGRESS: the encode band is split by FRACTION, not by absolute percentage, because `encodeFloor`
is 8 when the audio loudnorm analysis ran and 0 when it did not. The monotonic `EmitProgress` gate
(Section 9, FIX_1) means a mis-estimated split can only ever STALL the bar, never rewind it.

⚠️ MANDATE #1: the scratch master is NOT a cache — see the owner-approved carve-out at the top of
this file. It is created, consumed and deleted inside one job and can never outlive `tempJobDir`.
Do not delete this feature believing it violates the mandate, and do not use the carve-out to
justify anything that persists or is reused between exports.

------------------------------------------------------------------------------
5C.5 — THE SIZE-TARGET RETRY (AND WHEN IT IS SUPPRESSED)
------------------------------------------------------------------------------
`ProcessWorker` allows up to 2 attempts. If a size-locked export lands outside ±5% of the target,
attempt 2 scales the bitrate by the size ratio and re-renders — a blind guess that the code itself
acknowledges can land FURTHER from the target than attempt 1.

T01 SUPPRESSES THIS when a two-pass run produced the file: a real complexity map already
distributed the exact budget it was given, so burning another full render on a guess cannot beat
it. Worst case drops from ~2.7x to ~1.35x.

⚠️ The suppression is keyed on `twoPassProducedResult` — "did a two-pass run actually produce this
file" — and NOT on `lastSuccessfulEncoder == "libx264"`. Those are NOT the same thing: keying on
the encoder would silently disable the retry for ordinary single-pass CPU exports, which still
benefit from it. The retry remains fully intact for the NVENC/CQ paths.

------------------------------------------------------------------------------
5C.6 — OBSERVABILITY (G09) — READ THIS BEFORE DEBUGGING A SLOW EXPORT
------------------------------------------------------------------------------
Every export writes ONE INFO line naming the CHIPS, not just the codec:

  PIPELINE RESULT: decode=GPU (NVDEC/cuda) encode=GPU (NVENC) speed=3.4x route=two-pass(fast)

with an explicit "WARNING: this is the CPU fallback, the requested hardware encoder FAILED" suffix
when hardware encoding was requested and did not happen. The absence of this line was precisely why
two entire CPU-only exports went unnoticed on a machine with a working RTX. It carries no file
paths, so it is safe at INFO under logging invariant L8 (Section 4). DO NOT demote it to DEBUG.

⚠️ THE SHAPE IS IDENTICAL IN BOTH APPS, INCLUDING THE `route=` SUFFIX. `ProcessWorker` and
`MergerWorker` build this line the same way on purpose, so a person reading a log never has to
know which application produced a given line. The Merger's copy omitted `route=` at one point,
which made this documented format wrong for half the suite. Keep them in lockstep.

5D. THE AUDIO PIPELINE — EXPORT vs PREVIEW
------------------------------------------------------------------------------
FILES: `Media/AudioFilterChain.cs` (the whole music/game/voice mix) ·
       `Media/AudioLoudnessProbe.cs` (targets + measurement) ·
       `Media/ProcessWorker.cs` (game bus, meme, limiter, second pass) ·
       `Media/FilterGraphBuilder.cs` (SidechainCompressNode defaults) ·
       `MusicWizardWindow.axaml.cs` + `VoiceOverWindow.axaml.cs` (the PREVIEW side)

⚠️⚠️ THE ONE THING TO UNDERSTAND BEFORE TOUCHING ANY OF THIS ⚠️⚠️
THE PREVIEW AND THE EXPORT ARE TWO DIFFERENT ENGINES. The export is an FFmpeg filter
graph. The preview is mpv, and mpv is driven ONLY through the `volume` property — there
is not a single `af` (audio filter) call anywhere in the application. So the preview can
reproduce LEVELS and can never reproduce DYNAMICS. Everything below follows from that.

⚠️ THE TWO "CANNOT BE" ROWS ARE NOT LAZINESS. Ducking needs the game and the music inside
ONE filter graph so one can listen to the other. The preview plays the video and the music
through TWO SEPARATE mpv PROCESSES (`WizardVideoHost` and `_audioIpcClient`). Two processes
cannot hear each other. Simulating it would mean either pre-analysing the game audio and
riding the music `volume` from a 30 Hz timer (an approximation that sounds stepped on rapid
gunfire), or rebuilding the preview onto a single player with a real filter chain.
SO: TRUST THE PREVIEW FOR BALANCE, NEVER FOR DYNAMICS.

5D.1 — LOUDNESS: ONE TARGET, TWO PASSES, NO AGC
------------------------------------------------------------------------------
  * `AudioLoudnessProbe.TargetLufs = -14.0`, `PeakCeilingDbtp = -1.5`, `MusicBedLufs = -20.0`.
    -14 LUFS is the YouTube / TikTok / Reels / Shorts figure; platforms turn ANYTHING louder
    back down, so it is the ceiling of useful loudness, not an aggressive setting.
  * ⚠️ EVERY loudness number in the app now reads those constants. The measurement pass, the
    second pass and the "your video is too quiet" prompt used to disagree — the probe judged
    against -14 while the export mastered to -23 (EBU R128 BROADCAST), so the user was warned
    against one number and shipped another 9 dB away. DO NOT hardcode a target anywhere.
  * ⚠️ THE MEASUREMENT PASS MUST DECLARE THE SAME TARGET AS THE SECOND PASS. `input_i/tp/lra/
    thresh` describe the source and do not care, but `target_offset` DOES — and that offset is
    handed straight to the second pass.
  * ⚠️ NEVER add a `loudnorm` over the finished mix (AUDIO_01). One used to sit there with no
    measured values and no `linear=true`, which makes FFmpeg run its DYNAMIC mode — a
    continuously-acting AGC over the whole mix. Because a commercial music master (~-9 LUFS)
    is the loudest thing present, the MUSIC drove the gain of everything: every swell pulled
    the gunshots down, every dip pushed them back up. The ducking below was computed correctly
    and then silently overridden, producing the exact inverse of the intended effect.
  * QUIETBOOST_01 — ONLY 30% OF A POSITIVE LIFT IS ACTUALLY DELIVERED. `AudioLoudnessProbe
    .QuietBoostReductionFactor` (0.70) is subtracted back out as a single `volume=<dB>` on the
    FINISHED MIX, immediately before the limiter. A -32 LUFS capture asks for +18.00 dB and keeps
    +5.40 dB, landing near -26.6 LUFS instead of -14. Owner's decision: -14 is correct by the
    standard and was reported as far too loud on gameplay, where the noise floor and room tone
    come up with the lift. ⚠️ IT ONLY EVER REDUCES A BOOST — a capture already ABOVE the target is
    still pulled all the way down, because that direction is a ceiling and not a preference.
    ⚠️ IT IS APPLIED TO THE SUM, NOT THE GAME BUS. Music sits at an ABSOLUTE `MusicBedLufs` and
    the voice-over at an absolute target, so trimming the bus alone would leave both where they
    were and make them relatively LOUDER by exactly this amount; trimming the sum moves everything
    together and the balance in 5D.0 is untouched. THE PREVIEW DOES NOT SIMULATE IT — PREVIEW_03
    already shifts the whole preview down by a common offset, so the preview stays quieter than
    the export in absolute terms and exact in relative terms, which is what it is trusted for.
  * PROPORTIONALITY: when the game bus is lifted, music, voice-over and meme are shifted by the
    SAME dB, so the balance the user set with the sliders survives normalisation intact.

5D.2 — THE DUCKING CHAIN, IN ORDER
------------------------------------------------------------------------------
  1. Trigger source  : game bus AFTER the voice-over is mixed in, via `asplit`. So your voice
                       ducks the music too, which is what anyone would expect.
  2. Trigger shaping : `highpass=f=200,lowpass=f=3500` then
                       `agate=threshold=0.05:attack=5:release=100` then
                       `equalizer=f=1000:t=q:w=2:g=10`.
                       It listens for voice/action, not rumble, and is deaf to room tone.
  3. Music split     : `acrossover=split=250[mus_low][mus_high]`.
                       ⚠️ ONLY THE HIGH BAND IS DUCKED. Everything below 250 Hz is a permanent
                       shelter, which is what stops a ducked track going limp. This was 150 Hz
                       and covered the band where a gunshot's WEIGHT lives (~80-250 Hz), so the
                       music's body kept masking shots that the treble had politely made room
                       for. 250-300 Hz is the useful range; higher starts thinning the music.
  4. Ducker          : `sidechaincompress=threshold=0.15:ratio=8:attack=1:release=800:
                       detection=peak`  (`FilterGraphBuilder.SidechainCompressNode` defaults).
                       - ratio was 2.5 (a mix-glue setting; ~6 dB of reduction, inaudible as a
                         duck). 8:1 gives ~8.75 dB at the same overshoot.
                       - detection was `rms`, which AVERAGES — exactly wrong for gunfire, the
                         short sharp sounds that matter most. `peak` catches transients.
                       - release was 400 ms, so music surged back between individual shots and
                         "breathed". `sidechaincompress` has no hold parameter, so 800 ms
                         stands in for one. attack=1 ms was already correct.
  5. Reconstruct     : `[mus_low][mus_high_ducked]amix=weights='1 1':normalize=0`.
  6. Final mix       : game + reconstructed music, `weights='1 1':normalize=0`.
  ⚠️ TUNE IN THIS ORDER if it over-ducks: Ratio, then Release, then MusicBedLufs. Threshold
  LAST — it interacts with the bed level, so moving it first makes the other two unreadable.



5E. THE OUTPUT TIMELINE — THE ONE PLACE THAT KNOWS HOW LONG THE FINISHED VIDEO IS
------------------------------------------------------------------------------
`FortniteVideoSoftware.Core.Media.OutputTimeline` (TIME_01) is the SINGLE SOURCE OF TRUTH for
converting between SOURCE time (a position in the original file) and OUTPUT time (a position in
the finished, exported video). Nothing else in the codebase is permitted to re-derive this.

THREE FRAMES OF REFERENCE — mixing them up is the classic bug here:
  * ABSOLUTE SOURCE seconds     — position in the original file, trim offset included.
  * CLIP-RELATIVE SOURCE seconds— measured from the trim-in point, so the clip starts at 0.
  * OUTPUT seconds              — position in the finished video, AFTER speed and freezes stretch it.
`SourceToOutput()` takes ABSOLUTE source seconds. `OutputToSourceRelative()` returns CLIP-RELATIVE
source seconds. That asymmetry is not a design choice, it is the contract the existing callers rely
on and it was preserved deliberately.

⚠️ A FREEZE IS AN INSERTION, NOT A REPLACEMENT. This is the single most misunderstood rule in the
codebase. When the user freezes 5s-8s, the exported graph holds the frame at 5s for 3 seconds and
THEN CARRIES ON PLAYING FROM 5s. Nothing is skipped, and the finished video is 3 seconds LONGER.
In `GranularSpeedBuilder` this is the line `sourceCursor = fStart;` (NOT fEnd). Any future code that
advances a cursor past a freeze is wrong.

HISTORY — WHY THIS TYPE EXISTS. The same mathematics was previously hand-written in THREE places:
`GranularSpeedBuilder.CreateTimeMapper`, `GranularSpeedBuilder.Build`'s local `TimeMapper`, and
`MusicWizardWindow.MapPhase3OutputToSourceRelativeSeconds`. They drifted. The Music Wizard's copy
advanced its cursor past freezes (`cursor = Math.Max(cursor, segEnd)`), i.e. it believed a freeze
replaced the footage under it, so it under-reported the finished length by the whole freeze every
time. Measured, with the exported graph as ground truth:

  scenario                    EXPORT truth   Wizard said       ERROR
  no segments                     60.000s      60.000s     +0.000s
  slow-mo 10-20s @0.5x            70.000s      70.000s     +0.000s
  FREEZE 5-8s (3s)                63.000s      60.000s     -3.000s
  FREEZE 1.5s @20s                61.500s      60.000s     -1.500s
  two freezes                     63.000s      60.000s     -3.000s
  freeze + slow-mo                73.000s      70.000s     -3.000s
  base 2x + freeze                33.000s      31.500s     -1.500s
  fast 3x + 2 freezes             50.667s      46.667s     -4.000s

Slow motion always agreed; ONLY freezes diverged. Music was therefore being positioned against a
length the finished video never had. All three copies now delegate to `OutputTimeline`.

REVERSE MAPPING IS DELIBERATELY LOSSY INSIDE A FREEZE, AND THAT IS CORRECT. While a frame is held,
every moment of finished video shows the SAME source instant, so `OutputToSourceRelative()` returns
that instant. Callers that need to know whether the playhead is inside a held frame must ask
`IsHoldingFrameAt()` — do not try to infer it from the returned value.

⚠️ MPV PLAYS THE SOURCE FILE AND CANNOT PLAY THE FINISHED TIMELINE. Any ruler drawn in OUTPUT time
is therefore an app-driven clock backed by mpv: the app converts the scrub position to source time
and seeks mpv there. During a freeze the clock advances while mpv sits on one frame. This is not a
stall and must not be "fixed" by resynchronising the ruler to mpv's reported time.

PERFORMANCE NOTE: `OutputTimeline.Create()` allocates a small chunk list per call, and the Music
Wizard currently builds one per playhead update. This is comparable to the per-call list copy + sort
it replaced, but if a ruler is ever driven at frame rate the instance should be cached and rebuilt
only when the segment list, base speed or trim points change.


TIME_02 — THE GRANULAR EDITOR'S X AXIS IS NOW OUTPUT TIME. Everything the window STORES
(`_segments`, `_playheadMs`, `_freezeTimeMs`) is still SOURCE time; only the DRAWING changed. All 12
source->pixel conversions go through `SrcMsToX()` / `XToSrcMs()`, which route through a cached
`OutputTimeline` rebuilt only when the segment list, freeze or duration signature changes.
  ⚠️ THE EDITOR SYNTHESISES ITS OWN FREEZE SEGMENT. `_freezeTimeMs`/`_freezeDurationS` live OUTSIDE
  `_segments` and only become a Speed=0 SpeedSegment in MainWindow.axaml.cs:2538. A timeline built
  from `_segments` alone is BLIND to the freeze. `OutTimeline()` adds it. `_segments` are
  TRIM-RELATIVE, `_freezeTimeMs` is ABSOLUTE — hence the `- _trimStartMs`.
  ⚠️ THE FREEZE MARKER IS DRAWN AT `SrcMsToX(f) - holdPx`, NOT `SrcMsToX(f)`. The forward map
  already includes the whole hold, so the raw value is where the freeze ENDS. Drawing it there puts
  the camera icon on the replayed footage instead of on the freeze.
  THE FILM-FRAME LANE IS RE-LAID OUT, NOT REGENERATED. `ThumbnailStripGenerator` still samples
  evenly across SOURCE time; `RelayoutFrameLane()` then places ONE CLIPPING SLOT PER TIMELINE CHUNK
  at that chunk's OUTPUT position and width, with the strip scaled and offset inside the slot so the
  chunk's source window exactly fills it. Half speed spreads its frames over twice the width; a
  freeze shows the held frame stretched across the whole hold. A freeze chunk spans only a hair of
  source time by construction, so one frame's source duration is ESTIMATED from the strip geometry
  (strip height x 16:9 against strip width) rather than using the true span, which would magnify the
  image astronomically. The whole pass is wrapped in a try/catch that falls back to the plain
  stretched strip — a mis-drawn background must never block editing. The decoded bitmap is held for
  the window's lifetime (it is re-sliced on every relayout) and is disposed in `DeleteThumbStrip`.

FREEZE_CARET — THE CARET WALKS THE FROZEN SECONDS INSTEAD OF STEPPING OVER THEM. `SourceToOutput` of
the freeze instant is DEFINED to already include the whole hold, and every output moment of the hold
maps back to that same source instant, so a caret derived from `_playheadMs` sat pinned at the far
edge of the hold: it leapt the frozen span in one step the moment the freeze began and then did not
move for the whole duration. TIME_02 made the ruler longer by the freeze; the caret refused to cross
the space it added. The source position simply does not carry the answer during a hold, so it is
supplied directly through `_holdCaretOutSec` (non-null ONLY inside a held span; every path that
moves the playhead by ordinary means clears it). `PlaybackTimer_Tick` sets it to
`FreezeHoldStartOutSec() + elapsed` — the hold runs in REAL time and occupies exactly
`_freezeDurationS` of OUTPUT time, so elapsed wall-clock IS the offset into it, no conversion.
  ⚠️ THE `return` IN THE FROZEN BRANCH STAYS. The speed, icon and playhead code below it is all
  about MOVING footage and must not run while the picture is held — but the caret has to be updated
  BEFORE it.
  ⚠️ CLICKING INSIDE A FROZEN SPAN KEEPS THE CLICK POSITION. Deriving the caret back from the held
  instant sent it to the far edge, so the user pointed at one place and looked at another. Inside a
  hold (`IsHoldingFrameAt`), where the user clicked IS the answer.

FREEZE_ARM — WHY THE FREEZE PLAYED ONCE AND THEN SOMETIMES NOT AGAIN. The re-trigger guard was
`Math.Abs(currentAbsMs - _lastFreezeTriggerAbsMs) > 500` with the last trigger recorded as the freeze
point. It meant to say "do not re-fire the hold we just finished"; what it actually asks is "is the
playhead more than half a second from the mark", and on the SECOND pass the playhead crosses that
mark again at a distance of ~0, so the guard suppressed the freeze. Whether it fired depended on how
far the tick happened to overshoot — near the mark, suppressed; a slow frame that overshot by more
than 500ms, fired. Hence "sometimes". Replaced by `_freezeArmed`: "have we approached the mark from
behind it since it last fired?" has ONE answer, the same every pass, and it re-arms itself for free
on a rewind, a backwards seek or a replay. The crossing test also allows the previous tick to be AT
the mark (`prev <= freeze + 60`), because clicking the freeze marker parks the preview exactly on
that instant and a strict `<` meant the next Play could never satisfy "was before, now at or past" —
pressing Play while sitting on the freeze silently skipped it. `_freezeArmed` is what makes the loose
bound safe: it is cleared on fire, so this still fires only once per approach.

FREEZE_DRAG — THE FROZEN SPAN IS AN EDITABLE OBJECT, AND THE DRAG MATHS RUNS ON A FREEZE-FREE RULER.
`BaseTimeline()` is `OutputTimeline` over `_segments` ONLY. Dragging the freeze cannot be done in the
timeline the freeze is part of: inside the hold every pixel answers with the SAME source instant, so
the freeze pins itself and will not move, and as the duration changes under a resize every position
past the hold shifts so the pointer and the edge it is dragging chase each other. In the freeze-free
ruler the hold has zero width and the frame of reference is fixed for the whole gesture.
`OutXToBaseOutSec(x,w)` converts a pixel by passing pixels before the hold through untouched,
collapsing pixels inside it onto its start, and shifting pixels after it back by the hold.
  Gestures (resolved BEFORE speed blocks, because the band is drawn on top of whatever block it sits
  in and would otherwise be unreachable there): edge grips resize, body moves, three-zone hit
  resolution capped at a third of the span exactly as HITBOX_01 does for blocks. ResizeEnd reads the
  FULL ruler (the hold's END edge exists only there); ResizeStart reads the FREEZE-FREE ruler and
  pins the end at where it stood on press. Bounds 0.2s–10s.
  ⚠️ MARKER PRESSES CAPTURE THE LANE CANVAS, NOT THE MARKER. `RedrawTimeline` rebuilds the marker
  overlay on every drag step, so a pointer captured by a marker belongs to a control destroyed
  microseconds later and the drag dies on frame one. The canvas outlives every redraw.
  ⚠️ A BODY MOVE DOES NOT PRESERVE THE GRAB POINT, deliberately: a hold has zero width on the
  freeze-free ruler so there is nothing there to preserve, and every formula that tries feeds the
  hold's own new position back into the reading that placed it. What ships is stable and converges in
  one step — drag left and the leading edge tracks the pointer, drag right and the trailing edge
  does, holding still never jitters — and it matches what dragging the camera marker always did.
  FIXED IN PASSING: `MoveFreezeCameraToCanvasX` still used `(x / width) * durationSeconds`, a
  SOURCE-LINEAR reading of an axis that has been OUTPUT time since TIME_02 — wrong every time it ran,
  by however much the timeline was stretched to the left of the pointer, so dragging the camera
  dropped the freeze somewhere the user had not pointed. That method is now deleted outright; the
  marker feeds the same `FreezeDragMode` pipeline as the band's grips, because two code paths for
  "where did the user drop the freeze" is exactly how two answers drift apart.

  * Playhead-Follow Rule (MARK START/END): The caret playhead now follows a trim marker LIVE while it is being DRAGGED (Main App preview + Granular segment edges) — every drag move seeks the preview to the marker's current position via the coalescing `SeekInternal`, so the exact frame under the marker is shown in real time whether the video is paused OR playing (no pause-state change is forced during the drag). 7. ACTIVE ARCHITECTURAL DECISIONS
------------------------------------------------------------------------------
- Decision: Pure Code-Behind UI State (vs MVVM). Rationale: Allows for rapid prototyping and absolute control over granular canvas rendering coordinates, marker bounding boxes, and dispatcher timer ticks. Tradeoffs: Results in very large .cs files (e.g., MainWindow.axaml.cs), tighter coupling between UI and logic.
- Decision: FFmpeg + SkiaSharp for Overlays. Rationale: FFmpeg's built-in drawtext filter is highly limited for dynamic line-wrapping and BIDI/RTL text rendering. Generating a transparent PNG overlay via SkiaSharp in C# and feeding it to FFmpeg is vastly more robust. Tradeoffs: Minor disk I/O cost to save/load temporary PNGs to disk before muxing.

- ⚠️ DRIFT_01 — THE ZOOM LANDED SIDEWAYS OF THE RUBBERBAND (`GranularSpeedBuilder.cs`).
  SYMPTOM: in Portrait mode the exported zoom sat ~15px RIGHT of the box drawn in the Granular
  editor and the right edge of the box was clipped off-frame. Vertical was pixel-perfect.
  ROOT CAUSE — READ THIS BEFORE TOUCHING ANY `crop` IN THIS REPO: `vf_crop` DOES NOT HONOUR
  FRACTIONAL GEOMETRY. It truncates w/h/x/y toward zero and then masks them DOWN onto the chroma
  grid (`s->x &= ~((1 << hsub) - 1)`, i.e. `& ~1` for yuv420p). The builder emitted
  `crop=w='359.1111':h='202':x='1257.4444':y='724'` and FFmpeg silently used `w=358 x=1256`.
  Because the snap is FLOOR, not NEAREST, the error is a SIGNED BIAS, never noise: the sampling
  window always moves toward the origin, so the picture always lands right/down of where it was
  framed. The zoom then multiplies that error by `targetZ` and the portrait Canvas Trick
  multiplies it again — a 2px snap on a 134px box became ~15px on the 1080-wide file.
  WHY IT PRESENTS AS PURELY HORIZONTAL: in portrait `targetZ` is ALWAYS the height ratio
  (`resH / zc.H`, because a 2:3 box makes `resH/zc.H < resW/zc.W`). Therefore `cropH = resH /
  targetZ` is EXACTLY `zc.H` and `cropY` is exactly an integer — the vertical axis never rounds.
  Only the width carries the fraction. The bug is horizontal by construction.
  FIX, CONSTANT-ZOOM PATHS (freeze, instant, `BuildConstantZoomFilter`): `SnapZoomWindow` /
  `SnapExtent` emit a window that is ALREADY whole and chroma-aligned, so FFmpeg's snap is a
  no-op. The extent goes to whichever neighbouring EVEN value makes `centre - extent/2` even,
  which with an even `pad` offset forces an even `cropX`/`cropY`. THE CENTRE IS PRESERVED
  EXACTLY — it was the thing drifting; the extent moves <=2px (<1% of zoom strength), which is
  invisible. Verified: markers at source 1188/1255/1322 land at output 3.6/539.5/1075.4 in the
  live mpv preview, 17.4/556.4/off-frame as shipped, 4.5/540.4/1075.3 with the fix.
  FIX, SLOW-RAMP PATH: the origin is a per-frame EXPRESSION and cannot be pre-computed, so the
  quantisation is moved inside it — `round(v/2)*2` — which lands on the NEAREST even value and
  again makes FFmpeg's floor-and-mask a no-op. Measured over the ramp: mean error went from
  -1.10px (always leftward, worst -2.23 output px) to -0.03px, symmetric +-1.07. The ramp now
  also hands off to the held zoom without a step at the seam.
  ⚠️ DO NOT "IMPROVE" THE RAMP WITH `in_w`/`in_h`. It was tried and it renders SOLID BLACK: the
  preceding `scale=...:eval=frame` grows the picture every frame, but the LINK dimensions crop's
  expression sees are frozen at config time (measured: `in_w` reported 5120 — the pad width —
  while real frames were ~20800 wide). Any clamp or normalisation built on `in_w`/`out_w`
  collapses the crop into the black margin. There is deliberately NO clamp on the ramp path;
  FFmpeg clamps internally and the padded canvas guarantees the window fits.
  THE GENERAL RULE THIS ESTABLISHES: any geometry filter parameter that is COMPUTED rather than
  authored — `crop`, `pad`, `overlay`, `scale` — must be handed to FFmpeg as a whole number
  already aligned to the pixel format's subsampling. Never pass a float and assume it is honoured.
  If the value must be an expression, quantise INSIDE the expression with `round(v/2)*2`. A
  filter that floors what you gave it turns a rounding question into a directional artefact, and
  every magnification stage downstream scales that artefact up.

- SYNC_01 — CUMULATIVE A/V DRIFT ACROSS A LONG MERGE (`MergerWorker.cs`). THE MOST IMPORTANT ENTRY
  IN THIS SECTION FOR ANYONE TOUCHING THE MERGER. Symptom: merge many clips that are each perfectly
  in sync on their own, and the audio slides further out of sync the further into the output you go.
  * ROOT CAUSE — TWO INDEPENDENT `concat` FILTERS. The graph joined video with
    `[v0][v1]...concat=n=N:v=1:a=0[v_concat]` and audio SEPARATELY with
    `[a0][a1]...concat=n=N:v=0:a=1[a_concat]`. Each builds its own timeline by adding up only the
    lengths it was handed, and neither knows the other exists. Those totals are never equal:
    game-capture MP4s are variable-frame-rate, so the `fps=60` normalization re-times video onto an
    exact 1/60s grid while audio keeps its true sample-accurate length. Every clip contributes a few
    milliseconds of video-minus-audio difference, and with two concats those differences ACCUMULATE.
  * MEASURED. 12 synthetic clips, video 3.000s / audio 2.980s each, beep at every clip start,
    measured against the video timeline: OLD graph drifted -34.6ms at clip 2, -173.3ms at clip 6,
    -381.3ms at clip 12, -416ms worst — perfectly linear, the signature of accumulation. NEW graph:
    0.0ms at EVERY boundary.
  * FIX — ONE INTERLEAVED CONCAT: `[v0][a0][v1][a1]...concat=n=N:v=1:a=1[v_concat][a_concat]`.
    With `v=1:a=1` the filter treats each clip as a SEGMENT: it takes the longest stream in that
    segment, advances every output by that same amount, and pads the shorter audio with silence.
    Picture and sound are re-zeroed together at every boundary, so an error cannot survive past the
    clip that produced it, let alone accumulate.
  * ⚠️ DO NOT SPLIT THIS BACK INTO TWO `concat` FILTERS. It reintroduces the drift, and it looks
    perfectly fine on a two-clip test — it only shows up on a long merge.
  * SUPPORTING: `setpts=PTS-STARTPTS` / `asetpts=PTS-STARTPTS` are now UNCONDITIONAL, not only on
    the trimmed path (game captures routinely start audio a few ms off video, and that offset used
    to walk straight into concat on untrimmed clips); and
    `aresample=48000:async=1:min_comp=0.01:first_pts=0` after the join repairs any residual sub-ms
    gap by resampling instead of shifting everything downstream.

# PRODUCT SPECIFICATION & FEATURE REQUIREMENTS: AVALONIA UI .NET 9 AOT VIDEO EDITOR

## 1. Master Application Volume Control
**Description:** A main vertical volume slider located on the right pane of the application's opening screen. This controls the Windows OS process (PID) volume for the application's preview playback ONLY.
**Core Logic:** It must strictly isolate from and not affect the FFmpeg export pipeline. If the background music and video audio have different volume levels (set during Phase 3 of the Add Music Wizard), this master slider must act as a global multiplier, scaling both volumes proportionally to maintain their relative offset.
**Edge Cases:**
* **Edge Case A (Zero-Scaling Memory):** If the slider is dragged to 0% (mute), the application must cache the previous proportional values. Dragging it back above 0% must restore the exact offset, not default both tracks to equal volumes.
**Examples:**
* *Example 1:* Video is at 100% volume, Music is at 50%. User lowers master slider by half. Video preview sounds like 50%, Music preview sounds like 25%. FFmpeg output remains 100%/50%.
* *Example 2:* User drags master slider to 0% to answer a phone call, then drags it back up. The 2:1 ratio between video and music is perfectly preserved.

## 2. Marker Drag Event Triggers & Playhead-Follow
**Description:** Interactive timeline markers (`MARK START` and `MARK END`).
**Core Logic:** Dragging the markers continuously along the X-axis must NOT continuously fire the state-change event. The logic must wait for the `MouseRelease` (drop) event. Upon release, the application triggers a single state update, identical to clicking the physical "Mark Start" or "Mark End" buttons at that specific coordinate.
**Playhead-Follow Rule (applies to Main App AND Granular Speed Editor):** While a marker is being DRAGGED, the caret playhead follows it LIVE — each drag movement seeks the preview to the marker's current position (via the coalescing seek), so the user sees the exact frame under the marker in real time, whether the video is paused or playing (the drag itself does not change the play/pause state). When a MARK button is PRESSED (not dragged) while PAUSED, the caret seeks to the newly marked position; when PLAYING, a button press must not interrupt playback. (Legacy behavior where the MARK END button force-paused playback is removed.) Every marker drag release also writes a `RuntimeLog` entry with the exact timestamp. Additionally, simply clicking a Granular Speed Segment to select it does NOT snap the playhead; the playhead only snaps if the user actively drags and releases an edge/marker.
**Edge Cases:**
* **Edge Case A (Lost Focus):** If the mouse drag loses window focus or goes out of bounds before releasing, the marker should revert to its last known valid position or trigger the release event at the boundary limit.
* **Edge Case B (Marking During Playback):** Pressing MARK START/END during playback marks at the caret's live position — since the caret is already there, no seek occurs and playback continues seamlessly.
**Examples:**
* *Example 1:* User drags `MARK START` from 00:05 to 00:10. The UI semi-transparent gray area does not jump around wildly during the drag. Upon releasing the mouse at 00:10, the gray area and music synchronization update instantly.
* *Example 2:* User clicks and holds the marker but doesn't move it, then releases. The state updates as a standard click.
* *Example 3:* Video is paused at 00:03. User drags `MARK END` to 00:12 and releases. The playhead jumps to 00:12 and the preview shows that exact frame.
* *Example 4:* Video is playing. User presses MARK END at 00:15. The end trim is set and the video simply keeps playing past it, uninterrupted.

## 3. Marker Collision Physics
**Description:** Hard boundaries for timeline markers.
**Core Logic:** The `MARK START` and `MARK END` markers are strictly bound by each other's coordinates. The Start marker's X-axis value can never be greater than or equal to the End marker's value, and vice versa.
**Edge Cases:**
* **Edge Case A (Collision Handling):** Dragging one marker into another must act like hitting a "brick wall." The dragged marker stops exactly 1 minimum-unit (e.g., 1 frame or 1 millisecond) before the other marker, refusing to pass.
**Examples:**
* *Example 1:* `MARK END` is at 00:15. User drags `MARK START` to the right. The cursor may pass 00:15, but the marker stops dead at 00:14.999.
* *Example 2:* User attempts to click and drag `MARK END` to the left of 00:00. It hits a brick wall at the `MARK START` position (e.g., 00:05).

## 4. Audio Timeline Synchronization Accuracy
**Description:** Music note vertical alignment markers.
**Core Logic:** The vertical lines dropping from the music note icons to the timeline must sync with extreme precision to the exact millisecond of the audio track, bypassing standard video frame-rate snapping.
**Edge Cases:**
* **Edge Case A (Sub-Frame Rendering):** If a millisecond timestamp falls between two visual video frames on the UI timeline, the marker must render at the exact sub-pixel X-coordinate representing that millisecond, not jump to the nearest frame line.
**Examples:**
* *Example 1:* An audio beat drops at 01:05.123. The vertical line renders precisely at the X-coordinate representing .123, even if the nearest 60fps video frame is at .116 or .133.
* *Example 2:* User zooms in maximum on the timeline. The music line maintains its absolute position relative to the audio waveform, rather than shifting to snap to the grid.

## 5. Dynamic Time Badge Indicator
**Description:** A floating, ephemeral timestamp badge attached to the X-axis playhead (carrot).
**Core Logic:** While the playhead is being moved or dragged, a badge showing the exact current time follows the playhead. When movement ceases, a 1-second timer begins. After 1 second, the badge triggers a CSS/UI animation fading to 0% opacity.
**Edge Cases:**
* **Edge Case A (Micro-movements):** Any 1-pixel movement of the playhead resets the 1-second timer immediately and restores opacity to 100%.
**Examples:**
* *Example 1:* User drags the playhead rapidly. The badge reads "00:12:34" and updates in real-time, staying fully visible. User drops the playhead. One second passes. Badge fades out smoothly.
* *Example 2:* User clicks the timeline once. The playhead jumps, the badge appears for exactly 1 second, then vanishes.

## 6. Granular Speed Editor State Persistence
**Description:** Window memory and responsive sizing for the secondary Granular Speed Editor.
**Core Logic:** The window state (X/Y coordinates, width, height) is serialized and restored by `WindowBoundsHelper.Track()` (the same persistence engine as the other 7 tracked windows). On the very first open (no saved bounds) the window opens at the OS-default size constrained by its hard floor of `MinWidth=900` / `MinHeight=600`; there is NO hardcoded default size in code. On every subsequent open the exact saved bounds are restored (position re-applied after `Opened` to defeat the per-monitor-DPI handshake), with a continuous 700ms-debounced save on move/resize.
**Edge Cases:**
* **Edge Case A (Off-Screen Recovery):** Saved bounds are honored even across monitor changes; the window is recentered onto the main display ONLY when it would be COMPLETELY off every connected screen (e.g., its saved monitor was disconnected). The 900x600 minimum floor guarantees it can never restore to an unusable sliver.
**Examples:**
* *Example 1:* User on a 4K monitor resizes the window to 2000x1000 and moves it to the top left. They close it. Upon reopening, it appears exactly at 2000x1000 in the top left.
* *Example 2:* User's saved position was on a now-unplugged external monitor. The window detects it would be entirely invisible and recenters onto the primary display instead.

## 7. Tactile UI Prompts (Freeze Time)
**Description:** Visual guidance forcing the user to select a freeze duration.
**Core Logic:** Clicking the freeze image camera icon triggers a centralized `Popup` UI element displaying "SELECT FREEZE DURATION" inside a bordered container to draw the user's eye to the duration buttons. Layout note (current): the contextual Action Ribbon that used to occupy its own row was REMOVED to give the video preview back a full band of vertical space. The `FREEZE IMAGE` button and all six freeze-duration presets (0.5s–3.0s) now sit on the LEFT flank of the transport row itself, on the same line as `MARK START` / Play / `MARK END` (centred) and `ZOOM-IN` (right flank). The six presets are stacked as TWO ROWS OF THREE, matching the speed presets directly below them so the two blocks read as a matched pair. The standalone "DURATION" caption was dropped — the buttons are self-describing at a glance.
**Edge Cases:**
* **Edge Case A (Memory Leak Prevention):** The blink animation loop must run on a finite timer or iteration count (e.g., stops after 15 seconds or 10 blinks) and settle at a solid state or disappear, preventing infinite background rendering threads from consuming RAM.
**Examples:**
* *Example 1:* User clicks the freeze icon. The UI immediately flashes the top and bottom prompts, drawing the user's eye to the preset buttons. User clicks a duration; the text instantly disappears.
* *Example 2:* User clicks the freeze icon but gets distracted and walks away. The text blinks 10 times, then stops blinking and remains statically visible to avoid resource drain.

## 8. Persistent Directory Memory
**Description:** Smart probing and permanent caching of user file paths for NVIDIA Highlights and MP3s.
**Core Logic:** 1. `Upload Video`: Probe for `LocalApplicationData\Temp\Highlights\Fortnite` (or equivalent NVIDIA save paths). If found, default there. If not, fallback to OS `Videos` folder.
2. `Background Music`: Default to OS `Music` folder.
3. Once the user manually navigates to and selects a new folder for either, that specific string path is written to a persistent config file.
**Edge Cases:**
* **Edge Case A (Aborted Selection):** If the user opens the file picker, changes the directory, but then clicks "Cancel" (aborting the Add Music Wizard), the new directory path MUST STILL be saved as the default for the next time the window is opened.
**Examples:**
* *Example 1:* Fresh install. User clicks Upload. App detects GeForce Experience highlights and opens that exact folder automatically. User picks a video.
* *Example 2:* User clicks Add Music. They navigate from `C:\Music` to `D:\Downloads\TikTokAudio`. They realize they don't want to add music right now and hit Cancel. Next time they click Add Music, it opens directly to `D:\Downloads\TikTokAudio`.

## 9. Timeline Overlay Jitter Rectification
**Description:** Fixing Z-index and Cartesian coordinate math causing UI stuttering.
**Core Logic:** The yellow camera icon overlay on the X-axis timeline currently enters an infinite layout cycle (jitter/shaking) upon instantiation and hover, failing to release mouse capture cleanly during drag. This must be resolved by decoupling the icon's render position from the playback loop timer.
**Edge Cases:**
* **Edge Case A (Static Frame Jitter):** The mouse tracking math must utilize absolute canvas coordinates rather than relative deltas to prevent micro-stutters when the underlying video playback is completely paused.
**Examples:**
* *Example 1:* Video is paused. User hovers over the yellow camera overlay. The icon remains perfectly still. User clicks and drags it left; it moves smoothly 1:1 with the mouse pointer.
* *Example 2:* User drops the camera icon. The mouse releases immediately, allowing the user to interact with other elements without dragging the camera by mistake.

**Edge Cases:**
* **Edge Case A (Memory Purge):** Triggering this button must forcefully garbage collect all current timeline data, cached edits, temporary waveforms, and marker states, ensuring the UI is a clean slate before the system file picker dialog appears.
**Examples:**

## 11. Dynamic Processing Sliders
**Description:** `Speed Slider` and `Output File Size Slider`.
**Core Logic:** Two UI sliders. `Speed` sits to the right of the `PROCESS` button; `Output Size` sits to the left. They must be explicitly hidden (Collapsed/Display:None) upon application boot. The exact moment a valid video file is loaded into the timeline, their visibility toggles to true.
**Edge Cases:**
* **Edge Case A (Session Persistence):** Once unhidden, these sliders must remain visible for the entirety of the application's runtime. Deleting the video or clearing the timeline does not hide them again; only completely closing and restarting the application resets them to hidden.
**Examples:**
* *Example 1:* User opens the app. Looks at the bottom near the Process button. There are no sliders.
* *Example 2:* User drags and drops a video into the app. Instantly, the Speed and Output Size sliders fade into view. User later removes the video to upload a different one; the sliders stay visible on screen.

## 12. Click Priority and Hitbox Resolution
**Description:** Resolving overlapping elements on the timeline via Z-index and root inheritance.
**Core Logic:** The Granular Speed Editor's timeline must inherit directly from the main application's X-axis timeline object code to prevent duplicated, buggy logic. When multiple elements exist at the exact same X/Y coordinate, the mouse click event must respect a strict Z-index hierarchy, from highest to lowest:
1. Music Note Symbols (Highest priority)
2. Yellow Camera Overlays
3. Slider Playhead (Carrot)
4. MARK START / MARK END markers (Lowest priority)
**Exclusive Focus Rule (Granular Speed Editor):** Selection is EXCLUSIVE — exactly one object on the timeline holds focus at a time. Touching a yellow camera overlay gives it focus and takes it away from everything else; selecting a speed block takes it back. Focus is released in exactly three ways: pressing `Esc`, right-clicking anywhere in the window, or selecting a different object. All three run through one shared clear routine so they can never drift apart in behaviour. The marching ants CRAWL for as long as the object holds focus, not merely while it is being dragged — a static dashed outline reads as a border, whereas movement reads as "this is live and listening to your keyboard".
**Edge Cases:**
* **Edge Case A (Marching Ants Recovery):** When an element (like the yellow camera) is clicked and wins the priority check, it must regain its "marching ants" highlight state, allowing it to be nudged frame-by-frame via keyboard arrows.
* **Edge Case B (Esc With Nothing Selected):** `Esc` is only consumed when something on the timeline actually holds focus. With nothing selected the key keeps whatever meaning it has elsewhere in the window, so the shortcut can never swallow an unrelated action.
* **Edge Case C (Right-Click Over A Live Control):** The right-click release is detected on the way DOWN to whatever was clicked, not on the way back up. Detecting it on the way up would let any control that consumed the event block it, and "right-click anywhere" would quietly become "anywhere except the controls the user is most likely to be pointing at".
**Examples:**
* *Example 1:* A Music Note, the Playhead, and a Camera Overlay are all stacked perfectly on frame 300. User clicks that exact pixel. The Music Note is selected because it is highest in the hierarchy.
* *Example 2:* User clicks slightly below the Music Note hitbox, successfully hitting the Camera Overlay. It gains a dashed marching ants border and responds to the Left/Right keyboard arrows.
* *Example 3:* User grabs the freeze START camera (ants begin crawling on it), then clicks a 2x speed block. The camera's ants stop and the block takes the highlight — never both at once. Pressing `Esc`, or right-clicking on empty timeline space, leaves nothing selected.

## 13. Portrait Mode Visual Dimming
**Description:** Canvas visual aid for 9:16 aspect ratio conversion.
**Core Logic:** When the `Portrait` checkbox is ticked, the UI video player must dynamically draw a semi-transparent dark overlay (dimming) on the left and right flanks of the landscape video.
**Edge Cases:**
* **Edge Case A (Smart FOV Representation):** The clear, un-dimmed center vertical slice must accurately represent the backend FFmpeg logic. ⚠️ PORTRAIT CANVAS TRAP: the surviving width is exactly 720 pixels RELATIVE TO THE SOURCE (the 1280px figure is the INTERNAL portrait-space width; 1280 ÷ 1.778 scale = 720 source px — `CoordinateMath.cs` is the single source of truth, and `PhoneFrameMockup.axaml` dims 600+600px flanks leaving the 720px center clear on its 1920px canvas). Because the backend shrinks the height to create a 150px black void at the top (to write text), the resulting portrait video has a slightly wider Field of View (FOV) than a naive center-crop. The clear window must map this logic 1:1 visually — never "fix" the dimmer to 1280 source pixels.
**Examples:**
* *Example 1:* User checks the portrait box on a 1920x1080 gameplay video. The left and right edges instantly darken, showing the user exactly which UI elements (like minimaps or health bars) will be cut out of the final TikTok/Shorts render.
* *Example 2:* User unchecks the box. The dimming instantly vanishes, restoring the full 16:9 view.

## 14. Dynamic Text Wrapping Simulation
**Description:** Frontend preview of backend FFmpeg text rendering.
**Core Logic:** The UI must perfectly clone the backend's text-wrapping and scaling algorithms. As the user types into the text input, the preview text overlaid on the video canvas must dynamically shrink its font size or wrap to a new line exactly as the FFmpeg output will.
**Edge Cases:**
* **Edge Case A (Void Substitution):** Because the frontend preview does not physically render the 150px black void at the top of the canvas, the text must render in the top-center of the active video frame. It compromises on *position* to guarantee perfect accuracy of *scale and line-wrapping*.
**Examples:**
* *Example 1:* User types "Victory". It appears large and bold in the top center of the video. The user continues typing: "Victory Royale with 20 eliminations". The font dynamically scales down in real-time to fit the 1280px boundaries without breaking off-screen.
* *Example 2:* User pastes a massive paragraph. The logic detects the boundary hit, scales the font to the minimum threshold, and then executes line breaks exactly matching the FFmpeg word-wrap array, showing the user that their text is too long and will look cluttered.

## 15. Crash Recovery & State Serialization
**Description:** Robust session state saving and restoration mechanism across application crashes.
**Core Logic:** The application runs a background `RecoveryManager` that continuously serializes the current editing session state (including timeline edits, loaded paths, and marker locations) to a local recovery file. Upon a fresh application boot, the system checks for an existing unclosed recovery state and prompts the user to restore their previous session.
**Edge Cases:**
* **Edge Case A (Corrupt State Prevention):** If the recovery file is corrupted or partially written due to a hard system crash, the deserializer gracefully discards the invalid data and boots into a clean state without throwing a fatal exception.
**Examples:**
* *Example 1:* User is halfway through editing a complex video with music and markers. The power goes out. When the user reboots their PC and launches the application, their entire timeline, video, and audio sync are perfectly restored.
* *Example 2:* User normally closes the application. The system gracefully cleans up the recovery state file so the next launch starts fresh.

## 16. Advanced Audio Ducking & Sidechain Compression
**Description:** Professional FFmpeg mastering pipeline for dynamic audio mixing.
**Core Logic:** When background music is added alongside game audio, the FFmpeg rendering pipeline applies a PEAK-detecting sidechain compressor (`sidechaincompress=threshold=0.15:ratio=1.13:attack=1:release=800:detection=peak`, defaults overridable via config) fed by a cleaned trigger signal: the game audio is band-passed 200Hz–3.5kHz and noise-gated so only meaningful game sounds trigger ducking. 
**Ducking Ceiling (changed this session):** Previously, the trigger signal had a +10 dB equalizer boost at 1kHz. Because FFmpeg filters use floating point, this pushed peak gunshots up to +10 dBFS. Against a -16.5 dBFS threshold (0.15) and a 1.5 ratio, this forced an 8.8 dB ducking reduction. When combined with the 4 dB midrange cut from the "Carving" EQ, the music lost a total of 12.8 dB. A 12.8 dB drop leaves only 22% of the original amplitude, meaning the music suffered a catastrophic 78% reduction in perceived loudness. This aggressive pumping made the export sound highly unprofessional, effectively muting the music on every loud event. To resolve this, the +10 dB trigger boost was removed and the compressor ratio was softened to 1.13. The dynamic gain reduction is now precisely capped to a strict maximum of 20% during absolute peak gameplay moments, keeping the background music consistently present while still carving out just enough room for the game audio.
The music itself is first split at 250Hz via `acrossover` — the bass band bypasses ducking entirely (so the low-end groove never pumps) and ONLY the >250Hz band is compressed.
**Music Bed Level (added the same session):** the music is now loudness-measured and set to a background bed level (−20 LUFS) BEFORE the user's volume slider is applied. Previously music entered at whatever loudness its label mastered it to — a commercial master sits around −8 to −10 LUFS against a −14 LUFS game bus, so "music 100% vs video 100%" actually started the music roughly 5 dB AHEAD, and the ducking above was permanently fighting a deficit rather than doing its real job.
**Loudness Lift Ceiling (changed this session):** the export normalises the gameplay bus toward the −14 LUFS streaming standard, and on a quiet capture that lift can be very large — a −32 LUFS recording asks for +18 dB. Taking it in full is correct by the standard and was reported as far too loud: at −14 LUFS a gameplay clip is as loud as a mastered record, and its noise floor, room tone and controller clatter come up with it. Only 30% of a POSITIVE lift is now delivered (`AudioLoudnessProbe.QuietBoostReductionFactor = 0.70`), so that same clip keeps +5.4 dB and lands near −26.6 LUFS instead of −14. Two properties are deliberate. It only ever shrinks a BOOST — a capture already LOUDER than the standard is still pulled all the way down, because that direction is a ceiling rather than a preference and every platform turns a hot file down again anyway. And it is applied to the FINISHED MIX rather than to the gameplay bus alone: music sits at an absolute bed level and the voice-over at an absolute target, both independent of the bus, so trimming the bus by itself would leave them where they were and make them relatively LOUDER by exactly the trim. Trimming the sum moves every element together, so the balance the user set is bit-for-bit the balance they had before. The two-pass measurement itself is untouched.
**⚠️ PREVIEW LIMITATION:** ducking and EQ carving are applied on EXPORT ONLY. They are not, and cannot be, simulated in the preview: ducking requires the game and the music inside one filter graph so one can listen to the other, and the preview plays them through two SEPARATE media players that cannot hear each other. The preview DOES now reproduce the correct resting BALANCE (video, music and voice-over levels all match the export). Trust the preview for balance, never for dynamics.
**Edge Cases:**
* **Edge Case A (Silent Source Tracks):** If the game audio track is entirely silent or absent, the sidechain compressor must mathematically bypass the ducking logic, preventing the background music from improperly inflating or compressing against an empty signal.
**Examples:**
* *Example 1:* A loud sniper shot occurs in the game audio. The sidechain compressor reacts instantly, allowing the game audio to punch through clearly while momentarily dipping the background music.
* *Example 2:* During quiet exploration gameplay, the background music maintains its steady, normalized volume without being unnecessarily suppressed.

## 17. GPU Capability Probing (The Gatekeeper)
**Description:** Startup diagnostic to determine hardware encoding capabilities and limits.
**Core Logic:** The application executes a `GpuCapabilityProbe` upon startup before any rendering or FFmpeg operations are allowed. It queries the system for active hardware acceleration support (e.g., NVIDIA NVENC, AMD AMF).
**Edge Cases:**
* **Edge Case A (Seamless CPU Fallback):** If the user is on an unsupported GPU, virtual machine, or missing drivers, the probe intercepts the failure and forces a global fallback to software CPU encoding. The user experiences zero crash dialogs, just slower render times.
**Examples:**
* *Example 1:* User launches the app on an RTX 4090. The Gatekeeper detects NVENC, unlocking maximum hardware acceleration and the fastest possible render speeds.
* *Example 2:* User launches the app on a generic corporate laptop without a dedicated GPU. The Gatekeeper silently defaults to CPU encoding, ensuring the app still runs perfectly.

## 18. Deployment & Mutex Locks
**Description:** Strict OS-level locking to prevent overlapping operations.
**Core Logic:** `DeploymentLifecycle` implements a global system `MUTEX` that acts as a strict concurrency lock for installation and uninstallation processes. It ensures that only one instance of the installer/uninstaller or critical file-manipulation lifecycle can execute at any given time.
**Edge Cases:**
* **Edge Case A (Orphaned Mutex Recovery):** If a previous installation crashes mid-process and leaves an orphaned Mutex, the system must detect the dead owner process and forcefully claim the Mutex to unblock the user.
**Examples:**
* *Example 1:* User frantically double-clicks the installer five times. Only the first instance runs; the others detect the Mutex lock and gracefully exit, preventing file corruption.
* *Example 2:* User tries to uninstall the software while it is currently installing an update. The Mutex intercepts the request and warns the user to wait for the current operation to finish.

## 19. Intelligent Fake Mobile Preview & Portrait Canvas Simulation
**Description:** A dynamically adapting UI element that transforms the detached Preview Monitor into a high-fidelity, photorealistic mobile phone mockup when portrait mode is toggled, incorporating the math-driven "Portrait Canvas Trick."
**Core Logic:** When the main composition surface is landscape, the detached console (`PreviewMonitorWindow.axaml`) displays standard 16:9 full-screen content. When `Portrait` mode is engaged, the UI intelligently swaps states, wrapping the video in a physical smartphone structural mockup.
1. **The Phone Chassis (Glassy Reflection):** The mockup utilizes layered clipping borders (a nested inner frame with a semi-transparent `#1AFFFFFF` 4px stroke and a 40px corner radius) to simulate a physical, glassy smartphone bezel/reflection.
2. **The Mobile HUD Elements:** The grid injects a top Status Bar (9:41 clock, 5G signal bars mapped via proportional heights, Wi-Fi arch vectors, and a <50% battery icon) and a bottom Navigation Bar (Back, Home, Recents buttons).
3. **The Portrait Canvas Trick (Expanded FOV Padding):** The underlying video is NOT a naive 1080x1920 center-crop. To preserve a significantly wider horizontal Field of View (FOV), the source is mathematically scaled and cropped to exactly 1280px internal width. Because 1280px zoomed out to fit the 1080p horizontal constraint alters the vertical ratio, it naturally creates exactly 150-pixel black "voids" (padding) at both the absolute top and bottom of the final FFmpeg render. The Fake Phone UI intelligently reveals these precise 150px black voids, leveraging them as a canvas. The top 150px void space accommodates the SkiaSharp generated text overlay.
**Edge Cases:**
* **Edge Case A (HUD Airspace Priority):** Because the 150px voids are generated padding created by the Canvas Trick, the Top Status Bar and Bottom Nav Bar must sit exactly within these 150px black zones. This ensures the mobile OS HUD never overlaps or obscures the critical 16:9 gameplay footage sandwiched in the middle.
* **Edge Case B (Responsive Window Scaling):** If the detached window is resized or maximized by the user, the 720x1080 physical phone structure must maintain its strict aspect ratio and center alignment. The semi-transparent 600px side dimming blocks (`#99000000`) dynamically stretch to fill the remainder of the horizontal window space to block out the un-cropped landscape video, ensuring the glassy phone chassis never distorts or warps.
**Examples:**
* *Example 1:* User detaches the monitor while editing a standard 16:9 montage. The window behaves like a standard full-screen media player. The user clicks "Portrait Mode". Instantly, the flanks darken, a shiny smartphone bezel appears, mobile status icons manifest in the corners, and the video perfectly nests within the phone's "screen", exposing the 150px black canvas voids at the top and bottom.
* *Example 2:* The user types "New High Score!" into the text overlay box. The fake phone updates to show the text cleanly formatted, utilizing the canvas space generated by the 1280px zoomed-out FOV math, simulating exactly how the final TikTok or YouTube Short will look on a physical mobile device.

## 20. Video Merger Multi-Selection & Smart Scaling
**Description:** Robust list manipulation and dynamic font resizing for queued video items.
**Core Logic:** The Video Merger list (`SelectionMode="Multiple"`) supports multi-selection via `Ctrl+Click` (individual multi-select) and `Shift+Click` (range select). There is NO rubber-band drag-select — dragging on list items is reserved for reordering the queue (and external file drops). Long video titles are truncated with `TextTrimming="CharacterEllipsis"` (the full path is available as the item tooltip) so filenames never clip horizontally outside the `VIDEOS LIST` container; font size does not shrink.
**Lossless Output Sizing & Frame-Rate Unification:** Because a merge is a concatenation, the 100% ("Lossless") quality position must approximate the COMBINED size of the input clips (matching the on-screen "Est. Output"). The encoder anchors the VBR target `-b:v` to the duration-weighted AVERAGE source video bitrate, while `-maxrate`/`-bufsize` are raised to the PEAK single-clip bitrate for short-term VBR headroom on complex scenes. (Previously it anchored the WHOLE timeline to the PEAK clip bitrate, inflating the file far beyond the sum of inputs and forcing users down to ~40% quality just to hit a sane size — which destroyed quality.) Every clip is additionally normalized to a common `fps=60` (CFR) BEFORE concat, matching the encoder's 60-fps GOP, so mixed-frame-rate sources no longer stutter at the joins. (The unused `ffplay.exe` was also dropped from the dev-binary copy — music preview runs through an isolated `MpvIpcClient`.)
**Edge Cases:**
* **Edge Case A (Extremely Long Titles):** If a user imports a filename spanning 150 characters, the text is gracefully ellipsized ("My extremely long fil...") rather than wrapping or breaking the UI boundary constraints; hovering the item shows the complete path in a tooltip.
* **Edge Case B (Mixed Frame-Rate Sources):** Merging a 30fps clip with a 60fps clip no longer produces micro-stutter at the boundary; both are resampled to a uniform 60fps CFR before they are concatenated, so playback is smooth across every join.
**Examples:**
* *Example 1:* User highlights 15 video files in Windows Explorer, drags them into the app, then uses Shift+Click to highlight the bottom 5 videos and bulk-deletes them.

## 21. HUD Element Extruded Pad Borders
**Description:** Smart visual separation for overlaid HUD elements in Portrait Mode.
**Core Logic:** When the user crops HUD elements (e.g., Minimap, Health Bar) to overlay onto the 9:16 Portrait Canvas, the backend FFmpeg engine uses a padding algorithm (`-vf pad=iw+4:ih+4:2:2`) to paint a 2-pixel pure black border.
**Edge Cases:**
* **Edge Case A (Internal Overlap Prevention):** The 2-pixel border is strictly drawn *outside* the perimeter of the cropped HUD box. It never draws inward, ensuring that critical text/numbers inside the user's cropped box are not obscured by the border.
**Examples:**
* *Example 1:* A user crops their kill-feed. The background gameplay is bright and chaotic. The black extruded border guarantees the kill-feed "pops" off the screen with stark contrast against the background footage.

## 28. Intelligent Fade Margins & Persistence
**Description:** FFmpeg complex filter logic designed to intelligently apply video and audio fade transitions only when a sufficient video buffer exists.
**Core Logic:** The 'Enable fade in and out' checkbox controls global fade generation. When enabled, the FFmpeg builder dynamically calculates the available untrimmed footage ('pre-roll' before the trim and 'post-roll' after the trim). It requires a strict minimum buffer margin of 0.5 seconds to authorize the fade injection for that specific edge. If the user trimmed the video tightly without leaving a 0.5s margin, the logic purposefully disables the fade on that edge to guarantee the explicitly chosen action frames are not accidentally darkened. When disabled, the logic bypasses all fade injection entirely.
**Edge Cases:**
* **Edge Case A (Tight Asymmetrical Trim):** If a user leaves 2 seconds of buffer at the start of a clip, but 0 seconds of buffer at the end, the engine gracefully synthesizes a fade-in while actively declining to synthesize a fade-out.
**Examples:**
* *Example 1:* The 'Enable Fade' toggle is checked. The user trims the video from 00:05 to 00:10 on a 00:15 source video. Because 5 seconds of buffer exists before the start and after the end, flawless 1-second fade-in and fade-out effects are deployed.
* *Example 2:* The user sets the trim marker exactly at 00:00.000. Because 0 seconds of pre-roll buffer exist, the engine skips the fade-in filter completely so the video doesn't awkwardly fade up over their intended content.

## 29. Subsystem Integrations: Fades, Memes, and Speed
**Description:** The master Enable Fades toggle operates in tandem with several disparate application states (Memes, Speed Segments, Audio, Thumbnails).
**Core Logic:**
1. **Speed Multipliers**: When the video speed is altered (e.g. 2x speed), a 1-second fade requires 2 seconds of source frames. The builder dynamically multiplies padStartHumanSec * SpeedFactor to ensure the final output fade duration remains exactly 1.0 second in human-time, regardless of extreme speed warps.
2. **Meme Appending**: If a meme is concatenated to the end, the main video applies its normal fade-out. The meme then plays, and a completely separate fade-out is dynamically generated and applied to the meme's tail.
3. **Background Music Exemption**: Master video fades do NOT dictate music fades. Background music generated by AudioFilterChain always receives gentle 1.5s fade-ins and fade-outs. If a meme is present and music is allowed to continue over it, the music track dynamically stretches its duration, disables its internal fade-out, and applies a master audio fade exactly synchronized to the meme's final frames.
4. **Pitch-Black Thumbnail Prevention**: A fade-in starts with a pitch-black frame, which would normally cause Discord/YouTube to generate a black thumbnail. To bypass this, the engine extracts a single action frame, freezes it, and prepends it as a 0.1-second static intro BEFORE the fade-in starts. This micro-flash ensures web scrapers grab a beautiful thumbnail.
5. **Thumbnail Selection Algorithm**: If the user explicitly selects a thumbnail using the UI camera icon, that exact timestamp is used. If left blank, the engine mathematically defaults to extracting the frame located exactly 66% (2/3rds) of the way through the user's trimmed video segment (tStart + (tEnd - tStart) * (2.0 / 3.0)), guaranteeing a high-action mid-gameplay thumbnail.

## 31. Voice Over Studio & Smart Demographics
**Description:** A dedicated popup workspace allowing users to record real-time voice-overs completely synced to their video, featuring automatic DB normalization, demographic muting, and sidechain ducking.
**Core Logic:**
1. **Offline FFT Probing:** Upon launch, the engine uses NAudio to analyze the first 15 seconds of video offline. It performs a Fast Fourier Transform (FFT) to hunt for localized frequencies corresponding to Adult Male (125Hz), Female (210Hz), and Children (325Hz). Discovered demographics unlock muting checkboxes.
2. **Synchronization:** Users press 'V' to seamlessly record. NAudio precisely mirrors libmpv's playback state so the generated VoiceOver `.wav` stays locked to the timeline, even if granular 2x speed segments exist underneath.
3. **DB Matching & Burst Protection:** The engine applies FFmpeg's `loudnorm` filter to the voice-over track so it lands level with the gameplay. **Corrected this session:** it used to aim at the game's RAW measured loudness, but the game bus is itself normalised to the −14 LUFS standard a few steps earlier — so on a quiet clip the voice was aimed at the old, quieter number and ended up sitting exactly as far beneath the gameplay as the boost the game had just received. The quieter the source, the further the voice fell behind. It now targets the same −14 LUFS the game bus lands on, so the two arrive together. The `loudnorm` True Peak limiter simultaneously acts as a brick-wall to squash any sudden screaming bursts.
4. **Sidechain Integration:** Because the voice-over is structurally muxed into the base game audio track before the AudioFilterChain builds, the voice automatically benefits from sidechain compression, inherently ducking any background music the moment the user speaks.
5. **Timeline Granularity & Constraint:** The studio rigorously adheres to the user's previously defined `Mark Start` and `Mark End` trims. Background extraction tasks (waveforms/thumbnails) and MPV loop boundaries are hard-clamped exclusively to this active segment, preventing unnecessary generation of irrelevant video data.
6. **Multi-Session Recording & Mixing:** Users can record multiple disjointed or overlapping voiceover chunks. The UI tracks each session internally, drawing 40% semi-transparent red bounding rectangles over an interactive X-axis Timeline Ruler to visualize recorded zones. Upon "Apply", a background `ffmpeg -filter_complex` pipeline dynamically calculates precise `adelay` offsets relative to the trim-start and sub-mixes all chunks via `amix` into a single perfectly synchronized master voiceover track.
7. **Live Recording Indicator (fixed this session):** while the microphone is genuinely open, the red microphone button and the status light both PULSE (0.9s), the button carries a red glow, and the status text reads RECORDING. Previously the screen looked identical whether or not it was recording: the button had toggled a `recording` style class since the screen shipped and NO style for that class had ever existed anywhere in the application, so it changed nothing, and the only other cue was a 16px dot moving from 20% to 100% opacity of the same red — while its own tooltip promised "Red = recording, Green = idle", which it never was. The pulse is now the indication, and it is deliberately reserved for MICROPHONE OPEN: pressing record shows ARMING until the video actually rolls, and arming does not pulse, so the animation never claims to be capturing before a single sample exists.
8. **Recording Always Starts Or Always Says Why (fixed this session):** recording arms itself and opens the microphone on the first moment the video clock genuinely advances, which is what keeps a take locked to the timeline. If the preview refuses to start, that wait now gives up after 3 seconds and tells the user the video would not play. Previously one branch of that wait — the preview reporting itself paused or frozen — skipped the timeout entirely, so the screen could sit on ARMING forever: the microphone was never opened, and the empty recording was then discarded as "too short". A user saw no recording indicator and got no take, with no explanation for either.
9. **Take Playback Reliability (fixed this session):** recorded takes play back over the video in the studio so a take can be judged before applying it. The players were rebuilt whenever the take count and the player count disagreed, which silently assumed every take yields a working player — one unreadable file made the two numbers permanently unequal, so every player was destroyed and recreated twenty times a second and nothing was ever audible; the rebuild is now keyed on what it was last built FOR.
10. **Live Preview Synchronization & Time Mapping (added this session):** A dedicated `VoiceOverPreviewPlayer` ensures recorded audio plays back in flawless sync across *all* frontend workspaces (`MainWindow`, `GranularSpeedEditorWindow`, and `MusicWizardWindow`), automatically resolving multi-take offset tracking. If a user modifies video timing (e.g. accelerating a segment in Granular Speed), the VoiceOver is no longer invalidated/deleted. Instead, its start time dynamically re-maps via the active `timeMapper` and adheres precisely to the video frame where it was originally recorded, respecting all editor speeds during real-time preview.
11. **Waveform Monitor & Dynamic EQ (added this session):** A lightweight, 50ms dispatcher updates the voiceover visualizer without incurring any UI thread layout spikes. Thousands of generated Avalonia `Line` objects were replaced with a highly optimized `PathGeometry`, completely fixing previous app freezes and stuttering issues on apply. Additionally, the horizontal EQ meter scales and vibrates multiple vertical bars based on raw `NAudio` smoothed volume, drawing a real-time responsive Equalizer path instead of a static sliding width rectangle.
**Edge Cases:**
* **Edge Case A (Overlap Mixing):** If the user records two voiceovers directly on top of each other, the FFmpeg sub-mix cleanly blends them using `amix` instead of throwing an overwrite error.
* **Edge Case D (Preview Will Not Roll):** If the video refuses to start playing when record is pressed — a stalled decoder, a freeze frame at the playhead, or the clip already sitting at its end — the studio cancels the take within 3 seconds, deletes the empty recording and reports that the video would not start, instead of leaving the screen armed indefinitely.

## 32. Normalized Multi-Phase Progress Bar
**Description:** A unified, continuous 0-100% progress bar spanning entirely different backend operations without jumping or stuttering.
**Core Logic:** The FFmpeg `ProcessWorker` splits the global progress bar by REAL WORK, not by a fixed 50/50. Because audio Loudnorm analysis is fast and video encoding is the overwhelming bulk of the CPU/GPU cost, Phase 1 (Loudnorm 2-pass Audio Normalization) occupies only a small 0-8% band, and Phase 2 (Video Encoding) owns 8-96%; the final 96-100% is reserved for the file-copy + thumbnail tail so "100%" only appears when the deliverable is truly on disk. Within the encode band, progress is COST-WEIGHTED: a per-output-second cost map weights heavy stretches (zoom punch-ins — especially the SLOW ramp — and the per-frame crop chain) more than cheap stretches (freeze frames, plain passthrough, the cloned intro still), so the bar advances by work completed instead of by raw output timestamp. This removes the old behavior where the bar stalled on heavy zoom/slow chunks and raced on freeze/passthrough chunks. All progress is emitted through a single MONOTONIC gate (the bar can never move backward) and the UI eases the bar smoothly toward each new target (~33ms lerp), so bursty encoder reports never lurch.
**Edge Cases:**
* **Edge Case A (Skipped Audio Phase):** If the source video has no audio track, or the user set a manual volume offset (normalization coefficient `!= 0.0`), Phase 1 is skipped and the encode phase simply starts at 0% (not a dead jump to a mid-bar value) and drives 0-96%, so the bar never appears broken or "stuck".
* **Edge Case B (Target Size Multi-Attempt Resolution):** If a target file size needs multiple iterative FFmpeg attempts to hit the bitrate, the monotonic gate guarantees the bar NEVER snaps backward between attempts — a later attempt's raw reading can only ever hold or push the bar forward, so the render reads as one continuous sweep instead of resetting to the start of the encode band.

## 34. Asynchronous High-Volume Pipeline Logging
**Description:** Decoupled producer-consumer logging to eliminate UI thread lock-ups during multi-gigabyte FFmpeg status dumps.
**Core Logic:** The core `RuntimeLog` engine absorbs thousands of lines of output via an asynchronous `BlockingCollection<string>` (bounded at 10k; drops-with-warning under saturation rather than growing memory) and flushes them to disk on an isolated background Task. All three app processes (Main/Merger/Crop) forward Core-layer logs through `CoreLogger` into the same `RuntimeLog` and serialize their writes through a `Global\FortniteVideoSoftwareLogMutex` on a shared-append handle. Simultaneously, the UI `PhaseOverlayControl` ingests display logs into a `ConcurrentQueue` and utilizes a 1-second batching timer to safely dump them onto the visual textbox.
**Rotation & Bounded Retention:** The single active log is capped at 10MB and rotates BEFORE a batch would exceed it. Rotated `.old` files use a millisecond+GUID name so two concurrent processes can never collide on a rotation name (a whole-second name previously let a second process silently skip rotation). Retention trims by count (5 files), total size (~50MB) AND age (14 days) — whichever limit hits first — so total on-disk logging is firmly bounded.
**Privacy Gating & Fault Isolation:** Full FFmpeg/FFprobe commands and full input/output file paths log at DEBUG (dev-only, gated by `FVS_DEV_LOG_DIR`) so the production log never exposes the user's account name or folder layout; INFO keeps a safe operational trail (encoder/mode, file NAMES only, exit codes, GPU discovery, encoder/CPU-fallback reason, cancellation). Every write path swallows its own IO errors and the live on-screen `LogAppended` callback is exception-guarded, so a logging fault can never crash, freeze, or slow an export.
**Edge Cases:**
* **Edge Case A (Memory Leak Prevention):** Even while batching at high speeds, the UI textbox rigidly enforces the 100-line bounded FIFO constraint, guaranteeing that a 5-hour export will never crash the visual memory heap.
* **Edge Case B (Simultaneous Three-App Logging):** With Main, Merger and Crop Tools all writing at once, the global mutex serializes appends and the unique rotation names prevent any process from clobbering another's rotation, so no lines are lost or interleaved mid-line.

## 38. Interactive Speed Segment Physics & Timeline Collision
**Description:** Dynamic UI constraints governing the physical interaction, resizing, and dragging of colored speed segments on the Granular Editor X-axis timeline.
**Core Logic:** Speed segments render dynamically on the canvas as multi-hitbox elements (Left Handle, Center Body, Right Handle). Clicking any segment immediately promotes it to the active selection, updates its borders to yellow marching ants, and perfectly syncs the granular spinning wheel UI to its specific speed multiplier.
**Selected-Segment Edge Markers (Trim-Marker Clones):** The ACTIVE (selected) segment additionally renders two grabbable vertical START/END markers at its edges — an exact visual and behavioral clone of the Main App's MARK START/END trim markers (24px hitbox, 3px SeaGreen stick, resize cursor, hover highlight). Dragging them edits the segment's total length and position directly. These marker drags route into the SAME drag pipeline as block-edge resizing, so the collision physics, minimum width (200ms), RuntimeLog entries, segment list refresh, live preview speed mapping, crash-recovery serialization, and the final FFmpeg export all consume one identical code path — the change is millisecond-accurate on the X-axis from UI to output file. On drop while the preview is PAUSED, the playhead seeks to the edited edge (see §2 Playhead-Follow Rule); during playback the drag never interrupts.
**Persistence Chain:** Segments flow rel-ms (`_segments`, Granular) -> abs-ms (`ResultSegments`) -> Main App `_speedSegments` -> `SaveRecoveryState()` (invoked IMMEDIATELY on Granular Accept, so edits survive a crash right after closing the editor) -> `BuildExportSpeedSegments()` -> FFmpeg worker.
**Width-Aware Hit Resolution (all three gestures reachable at any block size):** A block's three hitboxes are proportional, not fixed. The grab zone for each edge is the SMALLER of 8 screen pixels and ONE THIRD of the block, giving every block a start third, a middle third and an end third no matter how narrow it is on screen. This matters because the minimum block is 200ms, which on a 60-second clip is roughly 3 pixels wide — with a fixed 8px edge zone the block sat entirely inside its own START zone, so its END edge and its draggable body were both unreachable and every click resized the start. When two grab zones are both in range (adjacent blocks touching at a shared boundary), the NEAREST one wins by actual distance rather than by whichever block comes first in the list, so the result no longer depends on segment ordering. The selected block's two green START/END marker sticks follow the same principle: each keeps its full 12px reach on the OUTSIDE of the block and surrenders only its inside half, capped at half the block width, so the two markers meet at the block's midpoint and can never overlap and steal each other's clicks.
**Edge Cases:**
* **Edge Case A (Social Distancing Barrier):** To prevent overlapping math errors, dragging a segment edge toward another segment acts exactly like a brick wall. The segment will halt unconditionally exactly `1000ms` (1 second) before colliding with the neighboring segment. It physically cannot overlap.
* **Edge Case B (Freeze Image Immunity):** The Freeze Frame camera icon is exclusively governed by its own independent X-axis logic (`_freezeTimeMs`). It is entirely immune to the speed segment `1000ms` brick-wall collision logic. A user can freely drag a speed segment completely through or directly over the freeze image icon without getting blocked.
* **Edge Case C (The Frozen Band Wins The Click Where It Overlaps):** The frozen span is drawn ON TOP of whatever speed block it sits inside, so it is also tested for a grab FIRST. Without that, a freeze placed inside a block would be permanently unreachable — visible, but answering to nothing. The block underneath stays fully grabbable everywhere the band is not.
* **Edge Case D (Rubber-Band Blocks Arrive Selected):** A block swept out with a drag is selected the moment it is released, with the speed wheel, the delete button and the marching ants already pointing at it. It previously arrived unselected, so the very next action the user wanted needed a second click on the object they were already pointing at — which reads as the drag having half-failed. The new block is located by matching its start/end, NOT by taking the last item: the segment list re-sorts on insert, so a block drawn to the left of an existing one is not last and an index would select the wrong block.
**Examples:**
* *Example 1:* User drags the right edge of a 2x Speed segment toward a 0.5x Speed segment. As the user drags the mouse, the yellow marching ants expand. Once the right edge is exactly 1 second away from the left edge of the 0.5x segment, the right edge stops moving, even if the mouse continues dragging to the right.
* *Example 2:* User drags the center body of a speed segment across the timeline. It seamlessly slides over the yellow Freeze Camera icon, disregarding it entirely, but violently stops when it gets within 1 second of another speed block.
* *Example 3:* User selects a 3x segment. Green START/END sticks appear at its edges. With the preview paused, the user grabs the END stick and drags it 2 seconds to the right; on release the preview snaps to that exact frame, the segment list updates, and the final FFmpeg export applies 3x speed up to precisely the new end timestamp.

## 41. Theme Token Governance & Font-Scale Resilience
**Description:** Two suite-wide UI mandates hardened this session across all three apps.
**Core Logic:**
1. **No Raw Hex In Shared Styles:** Every color in `AvaloniaApp.axaml`'s Styles section is a named DynamicResource token — button depth gradients (`AppPrimaryButtonGradient`, `AppSuccessButtonGradient`, `AppDangerButtonGradient`, `AppVoiceOverButtonGradient` + Hover variants), deep border brushes, hover overlays, CloseBtn states, and the slider-thumb glow edge. ## 42. Granular Segment Zoom-In (Spatial Attribute on a Speed Segment)
**Description:** An optional spatial "punch-in" attached directly to an existing temporal `SpeedSegment` (no separate track). Cropping a sub-region and scaling it back up produces a digital zoom on that segment only.
**Core Logic:** `SpeedSegment` (`GranularSpeedBuilder.cs`) carries optional `int? ZoomX/ZoomY/ZoomW/ZoomH` + `string? ZoomOrigRes` (plus a `bool ZoomSlow` ramp-mode flag, default `false`), threaded through `ChunkSpec` and the source-chunk split. A zoomed chunk injects `crop={ZoomW}:{ZoomH}:{ZoomX}:{ZoomY},cas=0.5,scale={srcW}:{srcH}:force_original_aspect_ratio=decrease,pad={srcW}:{srcH}:(ow-iw)/2:(oh-ih)/2:color=black` before framerate normalization. The AMD Contrast-Adaptive-Sharpening (`cas=0.5`) pass is MANDATORY — it restores edge micro-contrast lost to digital zoom on the GPU without heavy AI models. The live preview is GPU-CONDITIONAL (decided once at editor construction from `VideoRenderMode.Current.UseHardwareAcceleration`): on the GPU path, `UpdateLiveZoomCrop()` simulates the export zoom 1:1 live inside mpv via the `video-crop` property (instant snap or SLOW steal-up-to-1s ramp, mirroring the `GranularSpeedBuilder` ZoomPhase math; the yellow guide box is hidden since the real zoom is visible, and APPLY ZOOM-IN stalls behind a blocking "Applying changes..." busy overlay while the crop is primed). On CPU-only machines no `vf`/crop is ever applied (keeps playback pixels untouched, preventing CPU stutter) and the zoom shows only as the yellow UI overlay box.
**Canvas-Trick Geometry (concat-safe, distortion-free):** Granular chunks are concatenated at SOURCE resolution BEFORE the portrait stage, and FFmpeg `concat` requires uniform `WxH`. So `ZoomX/Y/W/H` are stored in SOURCE-resolution pixels (the drawn on-canvas box mapped through the video's actual letterboxed rect), and each crop is aspect-fit + black-letterboxed back to the source WxH: a 16:9 crop fills exactly (no bars); a 2:3 mobile crop scales to source height and is padded on the sides — bars the MobileFilterBuilder portrait center-crop (surviving width 720px = 1080×2/3) then removes, yielding a flawless distortion-free 2:3. Source resolution is read live from mpv (`MpvIpcClient.VideoWidth/Height`) for exact coordinate mapping.
**Interactive Editor (`GranularSpeedEditorWindow`):** a `ZOOM-IN` button (renamed from `SET ZOOM`) sits at the FAR RIGHT of the transport row (same line as `MARK END`), visible only when a segment is selected (`_selectedSegmentIndex >= 0`), toggling to "APPLY ZOOM-IN" (Primary->Success); directly beneath it are the two "Slow"/"Instant" ramp-mode checkboxes. `DELETE SEGMENT` and `CLEAR ALL SEGMENTS` are stacked at the bottom-right. The scrubber timeline sits on a semi-transparent black backdrop (`AppOverlayBrush`) so its tick grid reads like the Main App preview timeline. Zoom mode drops a dimmer with a dashed spotlight box supporting draw, center-pan and 4 corner scale handles. **Every zoom visual — the box, the handles and the timeline markers — is drawn in the single `AppZoomBrush` colour token (IDEA_6: one colour, one meaning).** This spec previously described a YELLOW box with DARK-BLUE (`#1e40af`) handles; those were three unrelated hard-coded colours that made a zoom indistinguishable from a speed segment, and the code now resolves them all through `GranularSpeedEditorWindow.ZoomBrush()`. The box is aspect-locked (16:9 landscape / 2:3 mobile via the Main App `PortraitModeCheckbox`, passed through new constructor args) with hard boundary clamping to the video edges and a 240x135 SOURCE-pixel floor (`ZoomFloorW`/`ZoomFloorH`). In Portrait Mode, the box is structurally clamped inside the "Portrait Canvas Brick Wall", guaranteeing users cannot select areas that will be cropped out.
On `PointerReleased` the box maps to source pixels and DESTRUCTIVELY overwrites the segment (sync guarantee so FFmpeg always pulls the latest coords). The segment now gains Detached Zoom Markers: a semi-transparent line and two independent magnifying-glass lollipop icons appear on the timeline, in the same `AppZoomBrush` colour as the box that created them. These zoom markers can be dragged independently of the green speed-segment boundaries, allowing the user to precisely dictate `ZoomStartMs` and `ZoomEndMs` regardless of the speed. A 3-time onboarding tutorial ("CLICK AND DRAG TO DRAW ZOOM BOX", dismissed on first press or after 1.5 seconds) is mounted at the top (Y:40) to avoid obstructing the video center. **CRITICAL UI FIX:** In Portrait Mode, the rubberband boundary logic now perfectly utilizes `(2.0 / 3.0)` to map 1-to-1 against the 720px surviving horizontal width of the "Portrait Canvas Trick", permanently eliminating vertical drift and restricted bounding boxes.

**Export Reliability (CRITICAL FIX):** the Granular editor's `OnClosing` used the suite's deferred-close pattern (`e.Cancel = true` + save bounds, then hide) but — unlike every sibling window — never set `_isSafeToClose = true` and never re-called `Close()`. The window therefore only HID; it never truly closed, so `await editor.ShowDialog(this)` never returned and the MainWindow continuation that copies `editor.ResultSegments` into `_speedSegments` never ran. Result: EVERY granular edit (speed segments, freezes AND zoom) was silently discarded at export and FFmpeg received only a uniform base-speed graph. `OnClosing` now sets `_isSafeToClose = true` and reposts `Close` on the next dispatcher turn, so results reach `_speedSegments` -> `BuildExportSpeedSegments()` -> `worker.SpeedSegments` -> the `GranularSpeedBuilder` split/concat graph as intended (and `OnClosed` now actually runs, disposing the editor's mpv preview host instead of leaking it every open).

**Confirming A Zoom (changed this session):** adjusting the box commits nothing — the zoom exists only once the floating green ✅ is pressed — yet the live preview follows the box the moment it moves, so users sized it, watched the picture punch in, and reasonably concluded they had finished. The ✅ is now noticeably larger (52 -> 76px, with matching type), and the instant a move or resize GESTURE ENDS it pulses gently for three seconds to say that it is still waiting. The pulse deliberately fires on release rather than continuously while dragging — a button flashing throughout the work reads as a fault, not a prompt — and a further adjustment inside those three seconds restarts a whole pulse rather than finishing a half-completed one.

**Timeline Legibility (changed this session):** two changes, both in the editor's timeline. The horizontal fuchsia zoom bar that used to be drawn across the segment block is REMOVED: it predates the paired zoom markers, restated the span those two magnifiers already show, and sat inside the block where it competed with the speed colour. And the "popsicle" markers — the yellow freeze cameras and the fuchsia zoom magnifiers — now drop their vertical stick all the way to the bottom of the lower timeline lane instead of stopping about halfway down the upper one. The heads stay exactly where they were, floating above the ruler; only the line beneath them is longer, so each marker reads as pointing at a precise instant straight through the timeline. A pair whose second head is staggered downward still finishes on the same bottom line as the first.

**Returning To The Main Screen (fixed this session):** setting a speed segment together with a zoom and then pressing APPLY SEGMENTS could freeze the entire application, with the console filling endlessly with OpenGL texture errors. The cause was a deadlock between the video preview's render thread and the interface thread during teardown: the render thread was holding a lock while waiting for the interface thread, and the interface thread was waiting for that same lock in order to shut the preview down. A zoom made it reliable rather than occasional, because both the zoom and the window closing force the preview surface to resize, and each resize makes the render thread issue a burst of exactly those waits at the moment shutdown begins. The preview is now shut down before the window is hidden — which is what closes the window of opportunity — and every hand-off between the two threads is bounded by a timeout with a defined give-up behaviour, so the same situation can no longer hang even if it is reached another way. The endless error stream is gone with it: the render loop now parks itself after several seconds of failing to present a frame instead of retrying fifteen times a second forever.

**SLOW vs INSTANT Zoom Ramp:** two mutually-exclusive "Slow"/"Instant" checkboxes sit under the `ZOOM-IN` button. The choice is stored per-segment as `SpeedSegment.ZoomSlow` (default `false` = instant).
- **INSTANT:** A hard-cut punch-in/out at the exact `ZoomStartMs` / `ZoomEndMs`.
- **SLOW (Smooth Camera Interpolation):** A gradual "camera" ramp fully implemented in FFmpeg via `ZoomPhase` tracking. It STEALS **exactly 0.5 seconds** of footage immediately BEFORE the `ZoomStartMs` to ease from full-frame in to the box, and **exactly 0.5 seconds** AFTER the `ZoomEndMs` to ease back out to normal. The range the user actually marked is held at full zoom for its whole length — the easing never happens inside it. 
  * **THE RAMP IS ALL-OR-NOTHING:** a side is granted the full 0.5s ramp only if it has at least 0.5s of free footage to steal; a side with less (e.g. the zoom sits at the very start or very end of the clip, or hard against a neighbouring zoom) gets NO ramp at all and snaps instantly. Each side is evaluated independently, so a single zoom can legitimately glide in and snap out. Free footage is measured against the NEIGHBOURING ZOOMS plus the clip start/end only — speed segments are ignored, so a ramp may run through a slow-motion or fast-forward stretch, and the geometric vectors are calculated correctly across those speed-adjusted chunks. 
  * **TWO ADJACENT SLOW ZOOMS REQUIRE A FULL 1 SECOND BETWEEN THEM** (`ZoomRampRequiredGapBetweenSlowZooms` = 2 x the ramp) before either is granted a ramp on the side facing the other, because both zooms want to borrow from that same gap: the earlier one needs 0.5s after it to glide out and the later one needs 0.5s before it to glide in. Closer than 1 second and NEITHER glides — both snap, symmetrically and predictably. This closed a real defect in which the two borrow windows were permitted to overlap; the chunk builder matches the FIRST zoom phase and stops, so the earlier zoom's glide-out claimed the contested footage and the later zoom's glide-in was partly or entirely discarded (measured: at 0.75s apart the picture eased out to normal, JUMPED straight to half zoom, then eased the rest of the way in — a visible hop resembling a rendering fault; at 0.5s apart the later zoom's glide was lost completely and it hard-cut in despite SLOW being selected). The doubled requirement applies ONLY when BOTH neighbours are SLOW — an INSTANT zoom, the clip start and the clip end borrow nothing and therefore never contest the gap, so the ordinary 0.5s minimum applies against them. 
  * **LIVE PREVIEW PARITY (GPU machines):** the zoom — INSTANT and SLOW alike, including both glides — is simulated live in the mpv preview on ALL THREE preview surfaces: the Granular Speed Editor, the Main App preview, and Music Wizard phase 3. One shared engine (`Media/ZoomPreviewSimulator`) performs the simulation and reads its timing constants directly from the export engine, so the three previews and the rendered file agree by construction rather than by discipline. In Music Wizard phase 3 the playhead runs on the OUTPUT timeline (already stretched by speed segments and freezes) while zoom times are SOURCE-relative, so the existing output-to-source mapping is applied before simulating — the zoom lands on the correct frame instead of drifting. The simulated crop is cleared whenever the segment set changes, a different video is loaded, phase 3 is left, or the wizard closes, so a deleted zoom can never linger over the wrong footage. 
  * **CPU-ONLY MACHINES DELIBERATELY DO NOT GET THIS** — they keep the static guide rectangles only. On the software render path every crop change forces mpv to rebuild its software scaler, and a single 0.5s glide causes roughly ten of them on hardware that has no GPU to begin with; the resulting stutter would be worse than no live zoom. 
  * One accepted difference from the export on every path: near the frame edges the export pads with black where the preview clamps the crop inside the picture. The Granular editor also CLAMPS zoom-marker drags to that same 1 second (mirroring the pre-existing 1000ms "social distance" enforced between speed blocks), so the crowded state is normally unreachable by dragging; switching a zoom to SLOW after it has been placed can still produce a tight pair, and that case is handled correctly by the ramp maths above (both simply snap — never a hop). 
  * HISTORY: the ramp was previously "up to 1 full second, or whatever is available if less", which produced a glide of unpredictable length between 0.5s and 1.0s and read as too slow for gameplay clips. The two governing values are `GranularSpeedBuilder.ZoomRampSeconds` and `ZoomRampMinAvailableSeconds`; they are public so the live mpv preview in the Granular editor reads the SAME numbers instead of duplicating them, guaranteeing the preview matches the export. 
  * CRITICAL PIPELINE FIX: The buggy FFmpeg `zoompan` filter was completely eradicated due to an unfixable 100% memory leak (even at `d=0`). It has been replaced by a mathematically pure combination of `scale=...:eval=frame` and `crop=...` that dynamically upscales the frame and crops the exact targeting window per-frame. This completely bypasses all FFmpeg internal sequence-caching bugs and operates with zero memory leakage. To prevent out-of-bounds crops when panning the camera to the edges of the video, the original frame is first padded with 1920 pixels of pure black (`pad=iw+3840:ih+2160:...:color=black`). Furthermore, the zoom mathematical ceiling evaluates both axes using `Math.Min(1920 / W, 1080 / H)` to perfectly match the `force_original_aspect_ratio=decrease` padding algorithm, completely eliminating the Portrait SLOW Zoom over-zooming logic error. To prevent the `concat` stitcher from destroying A/V sync with mixed framerates, *every* output chunk (zoomed or not) is rigidly normalized to `fps={targetFps}:round=near:start_time=0` at the very end of its filter chain (anchoring start_time=0 prevents VFR desync).
**Edge Cases:**
* **Edge Case A (Mobile Letterbox Round-Trip):** In Portrait mode a 2:3 zoom on a 16:9 source is scaled to source height and padded to 16:9 so the concat stays valid; the portrait pass then crops the exact centered 720px back out, so the final 9:16 video shows a clean 2:3 punch-in with no black bars and no stretch.
* **Edge Case B (Speed Change Preserves Zoom):** Re-dialing a zoomed segment's speed keeps its zoom box (record `with { Speed = ... }`), so a zoom is never silently wiped by an unrelated speed edit.

## 44. Detachable Preview Console (Every Preview Screen)
**Description:** Any screen that shows a live video preview can pop that preview out into its own floating window, and pull it back in again. Previously only the Main App could do this.

Detaching the Granular preview onto a second monitor does not drag the Main App's preview there next time. On the very FIRST detach for a given screen (nothing saved yet) the window is centred on the display the OWNING window is currently on, not the system's primary display — on a multi-monitor desk those are frequently different, and appearing on the primary would put the window on a screen the user is not looking at. From the second detach onwards the remembered geometry wins.
**Availability & Placement (never a dead click):** The button is never a trap. When there is nothing to pop out it is greyed out with a tooltip explaining why ("The video preview is still loading — there is nothing to pop out yet."), rather than looking live and swallowing the click. In the Main App the same rule now covers the menu entry as well as the on-video button — it reads "Load a video first" until a clip is open. ## 45. Merge Timeline Synchronization (Multi-Clip A/V Lock)
**Description:** When many clips are merged into one long video, picture and sound stay locked together from the first clip to the last.
**Core Logic:** Every clip is joined as a single SEGMENT carrying both its picture and its sound, so the two are re-zeroed together at each clip boundary. Where a clip's sound is very slightly shorter than its picture — normal for game-capture recordings, which are variable-frame-rate and get normalized to a fixed 60fps grid on the way in — the gap is filled with silence at that boundary instead of pulling everything after it forward.
**Edge Cases:**
* **Edge Case A (Clips With No Audio):** A silent clip is given a synthesized silent track of its own length, so it occupies the timeline correctly rather than collapsing the sound of everything after it.
* **Edge Case B (Offset Source Streams):** Clips whose audio stream starts a few milliseconds before or after their video stream are rebased to zero on both streams before joining, so a per-file offset never leaks into the merged timeline.
**Examples:**
* *Example 1:* User merges 30 gameplay clips, each perfectly in sync on its own. Previously the last clips drifted noticeably — measured at roughly a third of a second by clip 12 and growing linearly. The merged output now measures 0.0ms of drift at every clip boundary.
* *Example 2:* User merges a clip recorded with the microphone muted between two normal clips. The silent clip holds its full duration and the following clip's audio still starts exactly on its first frame.
## 46. Output Timeline — Truthful Finished-Video Length

**What it is:** one shared model (`OutputTimeline`) that answers two questions for the whole
application: how long is the FINISHED video, and which source frame is showing at a given moment of
it. Speed changes, freeze frames and the thumbnail still all stretch the finished video, and this is
the only place permitted to work out by how much.

**The rule that matters:** a freeze is an INSERTION, not a replacement. Freezing 5s-8s holds the
frame at 5s for 3 seconds and then carries on playing from 5s. Nothing is skipped and the finished
video becomes 3 seconds longer.

**Why it was built:** the same mathematics existed in three hand-written copies and they had
drifted. The Music Wizard's copy believed a freeze replaced the footage beneath it, so it
under-reported the finished length by the whole freeze duration every time — a 3 second freeze made
the real video 63.000s while the Wizard reported 60.000s, and at base speed 2x it reported 31.500s
against a true 33.000s. Slow motion always agreed; only freezes diverged. Background music was
therefore being placed against a length the exported video never had.

**Verification:** the forward direction was diffed statement-by-statement against the original and
is algorithmically identical (51 vs 51 statements, zero difference), so nothing that consumed it
changes. The new reverse direction was exercised at 54,000 sample points across 9 scenarios with a
worst round-trip error of 0.000000000s outside freezes, the correct held frame returned inside every
freeze, and the playhead never running backwards.

**Known limitation:** mpv plays the source file and cannot play the finished timeline. A ruler drawn
in finished-video time is an app-driven clock backed by mpv — during a freeze the clock advances
while the picture correctly holds one frame. That is intended behaviour, not a stalled preview.

**The caret crosses the frozen seconds (corrected this session):** because the reverse mapping is
deliberately many-to-one inside a hold — every output moment of a 1.5 second freeze maps to the SAME
source frame — a playhead derived from the source position could not move during the hold. It leapt
the whole frozen span in one step the instant the freeze began and then sat still for 1.5 seconds:
the ruler had grown by the freeze, correctly, and the caret refused to walk across the space it
added. The playhead position is now supplied directly while a frame is held, and advances in real
time across it. Clicking INSIDE a frozen span also used to kick the caret to that span's right edge,
leaving the user pointing at one place and looking at another; where the user clicked is now the
answer.

**Examples:**
* *Example 1:* User freezes a frame for 1.5 seconds in a 60 second clip. The finished video is 61.5
  seconds. Every ruler that reads from this model reports 61.5 seconds instead of 60.
* *Example 2:* User applies half-speed to a 10 second stretch and freezes a frame for 3 seconds. The
  finished video is 73 seconds; the Music Wizard previously believed 70 and placed music 3 seconds
  short of the true end.

## 47. The Frozen Segment As A First-Class Timeline Object

**What it is:** a freeze frame stopped being a marker at a point and became an object with a visible
extent, two grab handles and its own editing gestures — the same treatment every speed block on the
lane already had.

**Why it needed it:** the freeze is the one element in the editor that actually LENGTHENS the
finished video, and it was the only element on the timeline with no visible length at all. It could
be nudged whole by its camera icon, and its duration could only be chosen from six preset buttons.

**Seeing it.** The held frame is stretched across the whole hold on the thumbnail lane, which is
exactly what the exported file shows — and on its own that is unreadable, because a stretched frame
looks like slow footage or a glitch. Four cues carry the meaning instead, each doing a different job:
a cool blue wash in the same blue as the block above it, so both lanes read as ONE object; diagonal
hatching, which survives where colour alone does not (over a blue-ish frame, over a blown-out white
one, and for a colour-blind user); solid posts at both ends, because the wash says "something is
here" while the posts say exactly WHERE it starts and stops; and a centred ❄ FROZEN 1.5s label that
is dropped entirely rather than clipped when the span is too narrow to hold it.

**The floating marker.** A yellow camera "popsicle" hangs above the ruler at each end of the hold
with its stick dropping down into the lane — the same shape as the thumbnail mark on the Main App's
timeline, so it needs no learning. Two of them, not one, because a span with a single handle is a
span whose extent the user can only guess at.

**Editing it.**
1. **Drag either popsicle** — resizes from that end. The opposite edge stays exactly where it was.
2. **Drag either edge of the band** — the same resize, from the grips directly beneath the markers.
3. **Drag the band's body** — moves the whole freeze to a different moment of gameplay, length
   unchanged.
4. **Arrow keys** — with the END marker focused they trim the hold one frame at a time; otherwise
   they slide the whole freeze one frame at a time.
A hold is bounded to 0.2s–10s. The presets stop at 3s; dragging is the advanced path and gets more
room, but not unbounded — one careless sweep should not add a minute to the export.

**It reaches the exported file.** Every edit flows down one chain with no second copy of the logic:
the editor's freeze time and duration -> the Main App -> a Speed=0 speed segment synthesised at
export time -> the FFmpeg worker. An arbitrary dragged duration such as 1.83s survives to the render
unrounded. Each drag also ends by seeking the preview to the new mark, so what the user sees and what
FFmpeg produces cannot disagree.

**Edge Cases:**
* **Edge Case A (Freeze Inside A Speed Block):** the band is drawn on top of whatever block it sits
  in and is therefore tested for a grab first, or it would be visible but unreachable. The block
  underneath stays grabbable everywhere the band is not.
* **Edge Case B (Very Short Holds):** the grab zones are proportional, capped at a third of the span
  each, so a narrow hold still offers a start third, a middle third and an end third rather than one
  zone swallowing the other two.
* **Edge Case C (Moving A Hold):** the grab point is not pinned under the cursor during a whole-span
  move. Dragging left, the leading edge tracks the pointer; dragging right, the trailing edge does.
  This is deliberate — a held frame occupies no gameplay time at all, so "40% into the span" has no
  equivalent to preserve — and it matches how the camera marker has always behaved.

**Examples:**
* *Example 1:* User freezes a frame for 1.0s, then drags the END popsicle to the right. The band
  widens, the ❄ label updates to FROZEN 1.60s live, the ruler grows by the extra 0.6s, and the
  exported video is 0.6s longer than before the drag.
* *Example 2:* User drags the START popsicle to the left. The hold's end stays pinned exactly where
  it was and the freeze simply begins earlier — the frame that gets held is a different one.
* *Example 3:* User grabs the middle of the blue band and slides it to a different moment. The hold
  keeps its length; only the gameplay instant it interrupts changes. On release the preview jumps to
  the newly chosen frame so the user can confirm it.
* *Example 4:* User selects the END popsicle and taps the Right arrow ten times. The hold grows by
  exactly ten frames (10/60 s), which is the frame-accurate control the preset buttons cannot give.

## 48. Guided Walkthrough On Every Screen
**Description:** A short animated tour that points at the real controls on each of the six screens the first few times it is opened, and can be replayed forever afterwards.
**Core Logic:** `Controls/CoachOverlay.cs` is the engine and `Controls/CoachTours.cs` holds the six scripts as pure copy. A step dims the whole window except the control it is talking about, animates a ghost cursor performing the real gesture over it (point, click, drag, draw-a-box, drop-in), and floats a card with plain-English text next to it. Nothing is shipped as an asset — every frame is drawn from vector shapes on one 30Hz `DispatcherTimer`, so it survives the single-.exe mandate and follows the real layout at any font scale, theme or window size. Target rectangles are recomputed every tick because these windows are resizable. Registration happens on `Loaded` (before the first layout pass every control measures 0x0). Auto-shows the first 3 opens per screen, counted per screen in `UiStateStore`; SKIP or Escape burns the remaining showings. Every screen carries a permanent replay button — a "?" on the Merger, Crop Tools, Music Wizard, Voice Over and Speed Editor, and View › Show Me Around in the Main App.
**Edge Cases:**
* **Edge Case A (Missing Control):** A step whose named control no longer exists, or is currently hidden, does not throw — the overlay dims the whole window and shows the text as plain advice instead.
* **Edge Case B (Counter Honesty):** The "seen it" counter is incremented on the first frame that ACTUALLY PAINTED, not when the walkthrough was requested. The older zoom banner incremented before it laid itself out, so a user could burn all three showings without ever seeing anything.
* **Edge Case C (Click Protection):** The overlay is deliberately hit-testable across its whole surface. A stray click during a tour must never reach the live editor underneath and change the user's project.
* **Edge Case D (Non-Panel Root):** `CropToolWindow`'s root content is a `Border`, not a `Panel`. The host is resolved through `ResolveHostPanel`, which unwraps decorators — a naive cast would have silently disabled onboarding for that entire application.
**Examples:**
* *Example 1:* A brand-new user opens the app. The upload box lights up, a cursor drops onto it from above, and the card says "Drop a gameplay video straight onto this box." They press NEXT and the timeline lights up with a cursor sweeping across it.
* *Example 2:* A returning user forgets what ZOOM-IN does. They press "?" in the Speed Editor, choose SHOW ME, and the tour replays even though the automatic showings were used up months ago.

## 49. One Notification Style Across The Whole Suite
**Description:** Every screen reports what just happened the same way: a message that floats up over the video and fades out.
**Core Logic:** `Controls/FloatingNotice.cs` owns the only notification in the suite. It draws into the window's `OverlayCanvas` when one exists and creates an equivalent canvas on demand when it does not, so a window needs no XAML to gain notifications. Four colours carry meaning: green success, blue info, amber warning, red error. **Replaced five separate mechanisms** — the Main App's `Popup`, the Music Wizard's 98-line hand-rolled toast, the Merger's queue line, the Crop Tools status line and the Voice Over label — which meant a user had to learn a new place to look on every screen.
**Edge Cases:**
* **Edge Case A (Drag Spam):** The Speed Editor calls its status line from pointer-move handlers with text that changes every frame. Those deliberately do NOT float; only discrete events do (`Notify`/`NotifyError`). Floating them would stack a new pill over the video several times a second.
* **Edge Case B (Repeat Suppression):** Identical text inside 1.4 seconds is dropped, and at most three notices are alive at once — the oldest is retired early rather than letting a burst pile up unreadably.
* **Edge Case C (First Notice Placement):** A pill inside a Canvas has no layout slot, and on the first notice of a session the host canvas may itself still measure 0x0. It is placed twice — best-effort immediately, then correctly on the first animation frame — otherwise the very first message a user ever sees lands in the top-left corner.
* **Edge Case D (Window Torn Down Mid-Rise):** Every window clears its notices in `OnClosed`, so a rising message cannot keep animating against a dead visual tree.
**Examples:**
* *Example 1:* User deletes a take in Voice Over and sees "Take deleted" float up over the video — the same motion, place and style they already know from marking a trim point in the Main App.
* *Example 2:* A recording is too short to keep. Instead of being discarded in total silence, a red "That take was too short to keep" floats up.

## 50. Destructive Actions Actually Ask First
**Description:** Nothing that cannot be undone happens on a single click without a real, readable question.
**Core Logic:** Every destructive button in the suite is listed on Settings › Confirmation Dialogs and defaults to protected. The outer button acts ONLY when the user has switched that confirmation off; otherwise the confirmation is the sole path through. Dialogs are large, name exactly what is about to be lost (which block, which times, which speed, how many), state plainly that it cannot be undone, and offer an explicit escape ("KEEP IT" / "KEEP THEM" / "STAY HERE").
**Edge Cases:**
* **Edge Case A (The Flyout Trap):** An Avalonia `Button` that owns a `Flyout` opens that flyout by itself AND still raises `Click`. The Speed Editor's DELETE SEGMENT and CLEAR ALL SEGMENTS previously destroyed the work on that click and then popped an "are you sure?" whose CONFIRM button was wired to nothing. Destructive work must never live in the outer button's `Click` handler.
* **Edge Case B (Switching Tools):** Opening the Video Merger or Crop Tools closes the editor, so it asks first — but ONLY when real work exists. A freshly uploaded video with nothing marked is not work and switches instantly with no prompt.
* **Edge Case C (Consistent Defaults):** The Merger's two confirmations shipped defaulting to OFF while the Crop Tools' shipped ON, so identical-looking red buttons behaved differently out of the box. All now default to protected.
**Examples:**
* *Example 1:* User clicks CLEAR ALL SEGMENTS. A dialog says "All 6 speed block(s) on the timeline, including 2 zoom(s), will be erased… Your frozen frame and your video file are not touched." They press KEEP THEM and nothing is lost.
* *Example 2:* User with trim marks set clicks VIDEO MERGER. They are told the editor will close, that their edits are saved and will come back, and are given STAY HERE. On confirming, the editor stays on screen behind an "Opening Video Merger…" curtain until the merger's window is really up.

## 51. Product Identity, Press Feedback And Theme Integrity
**Description:** The shipped file introduces itself to Windows, every button in every window responds to a press, and both custom-drawn controls follow the selected theme.
**Core Logic:** The `.exe` carries real Win32 metadata (product, publisher, version, copyright) and `Build.cmd` contains a dormant Authenticode step that activates when `FVS_SIGN_PFX`/`FVS_SIGN_PASS` are set, signing and timestamping the binary. Press feedback is installed once as a single class handler on `Button` (`Tactile.EnableGlobalRipple`), covering every window and every code-built button; its colour is a theme token, white on dark surfaces and black on light. The quality dial and the volume tube resolve all of their chrome from `AppDial*` / `AppTube*` tokens.
**Edge Cases:**
* **Edge Case A (Dark Theme Must Not Move):** Every Dark-theme token value is byte-identical to the hard-coded hex it replaced, so the default appearance is unchanged to the pixel. Only the Light theme is new.
* **Edge Case B (No Double Ripple):** Because the ripple is a class handler, the per-button `Tactile.IsRippleEnabled` attribute must NOT also be set — both firing on one press draws two ripples. Use `Tactile.IsRippleSuppressed` to exclude a control instead.
* **Edge Case C (Disabled Buttons):** A disabled button does not ripple. Feedback that fires when nothing happened teaches the user to distrust it.
* **Edge Case D (Signing Is All-Or-Nothing):** If a certificate is configured but signing fails, the build FAILS. Silently shipping an unsigned binary when the operator asked for a signed one is the worst of the three outcomes.
**Examples:**
* *Example 1:* User downloads the .exe and right-clicks › Properties › Details. It names the product, the publisher and a version instead of showing a blank tab.
* *Example 2:* User switches Settings › Appearance › Theme to Light. The volume tube and quality dial repaint in light metal instead of staying two black slabs on a white window.

## 52. Automatic 66% Thumbnail Selection (WhatsApp Intro Safe-Zone)
**Description:** If the user does not select a custom thumbnail, the software mathematically computes exactly 66% (2/3rds) into the trimmed segment and uses that frame for the 0.1s intro.
**Core Logic:** The logic automatically prevents the "black screen" or "boring first frame" problem that occurred when falling back to Trim Start. Whenever the user moves either the Start or End marker on the timeline, a live event triggers UpdateAutoThumbnailMarker(), which recalculates the 66% mark (_thumbnailPosMs = Start + (End - Start) * 0.6666) and physically moves the Thumbnail Camera Icon to that new position. This way, the user can see exactly which frame will be grabbed.
**Edge Cases:**
* **Edge Case A (Human Override Protection):** If the user explicitly clicked "Set Thumbnail" (meaning ThumbnailSet = true), they have made a deliberate human choice. The auto-66% calculation disables itself and will NOT overwrite their custom placement when they adjust trim markers.
* **Edge Case B (No Secret Math):** The 66% logic is not hidden inside the backend exporter-it is wired directly into the UI's PointerMoved events. This ensures that what the user sees on the timeline is exactly what FFmpeg receives via payload.ThumbnailPosMs.
* **Edge Case C (Crash/Recovery Persistence):** Because _thumbnailPosMs is explicitly calculated and updated on every drag, SaveRecoveryState() persists the 66% auto-calculated timestamp. If the app crashes, the user restores right back to that exact timestamp.
**Examples:**
* *Example 1:* User drags Start to 10s and End to 40s. The Thumbnail Camera Icon automatically slides to 30s (the 66% mark of the 30s clip). The user shares the clip on WhatsApp and the preview shows the 30s mark.
* *Example 2:* User sets a custom thumbnail at 15s. They then drag the End marker to 50s. The Thumbnail Camera Icon stays frozen at 15s because they manually overrode the system.
